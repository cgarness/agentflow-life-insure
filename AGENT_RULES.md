## 3. Multi-Tenancy Rules

- Every tenant row carries **`organization_id`**. RLS uses **`public.get_org_id()`** from the JWT.
- **Super Admin:** platform console can list all `organizations`; in-app data for super-admins is scoped to their **home org** except Agencies tooling (see migrations `20260430203000_*`).
- **Admin:** all rows in their `organization_id`.
- **Team Leader:** downline via `ltree` / `is_ancestor_of` where policies allow.
- **Agent:** `user_id = auth.uid()` (and campaign-type rules on `campaign_leads`).
- **Queries:** `.maybeSingle()` for singular lookups that may return zero rows.
- **Never** expose `SUPABASE_SERVICE_ROLE_KEY` in the browser.

### Downline profile scoping is query-enforced, not RLS-enforced

Current downline profile scoping is **query-enforced, not RLS-enforced**. Because `profiles_select_org` permits same-organization profile reads, any feature requiring downline-only visibility must **explicitly constrain every query and schema-fallback path to the resolved allowed profile IDs** and must **fail closed if scope resolution fails**. **UI filtering must not be represented as a database authorization boundary.**

### Platform-level roles (Control Center)

- Platform-level roles live on **`profiles.platform_role`** (nullable text). v1 enum: `NULL` or `'platform_admin'`. Future values: `platform_manager`, `platform_viewer` — extend the CHECK constraint in a new migration.
- `platform_role` is **independent** of the agency role string (`Agent` / `Admin` / `Team Leader` / `Super Admin`) **and** of `is_super_admin`. `is_super_admin` = AgentFlow staff with cross-org tenant power; `platform_role` = AgentFlow staff with internal-ops (Control Center) visibility. **Do not auto-promote one to the other.**
- Control Center RLS uses **`public.is_platform_admin()`** which reads `profiles` directly — **not the JWT**. The role takes effect on the next request without a token refresh / `custom_access_token_hook` change.
- Control Center records live under the `control_center_*` namespace (`control_center_features`, `control_center_issues`, `control_center_health_checks`, `control_center_health_check_runs`, and the `control_center_tracker_*` Tracker tables — `systems`, `items`, `issues`, `marketing_claims`, `references`). `organization_id` is nullable on these tables; v1 records are platform-global (org-null).
- **Known exception (intentional, do not "fix"):** Control Center tables are **platform-global** and RLS-gated on `public.is_platform_admin()` — NOT scoped by `organization_id` / `public.get_org_id()`. This is the one approved exception to the "every table scoped by `organization_id`" rule. The `control_center_tracker_*` tables (added 2026-06-05) keep `organization_id` nullable for forward-compat but are org-null in v1; their derived `completion_percent` is intentionally NOT stored (computed in the UI from item statuses). Do not rewrite these policies to org-scoping or add org-NOT-NULL constraints without Chris's approval.
- Control Center routes (`/control-center/*`) are mounted **outside** the CRM `<AppLayout />` shell. Do **not** add Control Center links to the CRM sidebar.

## 4. Architectural Invariants

Non-negotiables from production:

1. **Twilio Voice JWT** — Sign with **`TWILIO_MASTER_ACCOUNT_SID`** as JWT `sub`. Subaccount SID in `sub` causes **ConnectionError 53000** (TwiML App is on master).
2. **`verify_jwt: false`** on Edge Functions called from the frontend (and webhooks). Validate Bearer JWT in Deno via `createClient(url, ANON_KEY).auth.getUser(jwt)` because Supabase gateway rejects ES256 when `verify_jwt = true`.
3. **Atomic queue claiming** — `SELECT … FOR UPDATE SKIP LOCKED` in the **canonical** `get_next_queue_lead` (see invariant #15; `fetch_and_lock_next_lead` is now a deprecated wrapper). Never fetch-then-lock in application code.
4. **Edge deploys** — Always `get_edge_function` (MCP) before deploy; ship full `index.ts` body.
5. **Migrations** — File on disk ≠ applied. Confirm with **`list_migrations`** (MCP) before assuming schema.
6. **Feature before permissions** — Ship working UI/data path, then tighten RLS/PermissionGate.
7. **Twilio webhook URLs** — Derive from **`SUPABASE_URL`** in all five voice/recording webhook functions; change all together.
8. **Canonical call duration** — `twilio-voice-status` is the **sole writer** of `calls.duration`; it is the canonical source for billing minutes, contacted logic, talk time, and reporting. Browser timers are UI-only and must not write `calls.duration` (P0B, 2026-05-28, removed all three `TwilioContext.tsx` writes — `finalizeCallRecord`, `checkOrphanedCalls`, `hangUpOrphan`; those paths still write `status`/`ended_at`. In `twilio-voice-status`: prefer `CallDuration`, fall back to `DialCallDuration`; terminal non-answer statuses (`no-answer`/`busy`/`canceled`/`failed`) with no Twilio duration write `0`; a late/out-of-order callback must never regress an existing positive duration (monotonic guard). `call_logs.duration` and `dialer_daily_stats.*duration_seconds` are separate telemetry and may still be browser-derived.

- **`public.profiles` authorization columns are NOT user-editable.** Three independent layers enforce it and all three must stay: (1) **grants** — `anon` has no privileges at all, `authenticated` has SELECT + a **column-scoped** UPDATE that excludes `id`, `organization_id`, `hierarchy_path`, `created_at`, `last_login_at`, `twilio_client_identity`, `welcome_email_sent_at`; (2) **RLS** — every write policy is `TO authenticated` with an explicit `WITH CHECK` (never `TO PUBLIC`, never a missing check, and **never** an always-true `WITH CHECK`); (3) **`enforce_profile_field_authorization()`** — a `BEFORE INSERT OR UPDATE` guard that raises when a protected column actually changes and the actor is not authorized. **Never "simplify" this to a single layer.**

22. **The Dashboard callback feed is DUAL-SOURCE; canonical-only is unsafe today (Dashboard Closeout Build 1 correction, 2026-08-03)** —
- Two live writers persist callbacks to **different tables**, and neither may be dropped:
  - **Campaign callbacks → `campaign_leads`.** `DialerPage` → `advance_campaign_lead` writes the canonical `callback_due_at` / `scheduled_callback_at` (compat) / `callback_agent_id` / `callback_note` (invariant #16). **Ownership = `callback_agent_id`.**

- **PostgREST cannot filter/order/paginate on SQL `COALESCE`**, so campaign callbacks are read as **two mutually exclusive branches** — `callback_due_at IS NOT NULL`, and `callback_due_at IS NULL AND scheduled_callback_at IS NOT NULL` — each bounded and ordered by its own column. A row appears exactly once and `callback_due_at` always wins when both are set. **Never** try to `.order("coalesce(...)")`.
- **Paginate after the merge.** Fetch each branch to `offset + pageSize`, merge, order globally (`dueAt ASC`, stable source rank, `id ASC`), then slice. Offsetting each source independently and concatenating creates gaps/duplicates wherever sources interleave.
- **Exclude terminal `campaign_leads` statuses** (`DNC`/`Completed`/`Removed`/`Failed`, per invariant #15) — a terminal lead can retain a stale callback timestamp.

Appointment callbacks are owned by **`appointments.user_id`**, which is **authoritative whenever populated**. But the current `FloatingDialer` quick-call insert sets **`created_by` and NOT `user_id`** (`appointments.user_id` is nullable, has **no default**, and **no trigger backfills it** — live triggers are `appointments_updated_at` plus two workflow dispatchers, none of which touches it). `appointments_select` RLS already exposes such a row via its `created_by = auth.uid()` branch, so the Dashboard predicate must be:
  ```
  (user_id = uid) OR (user_id IS NULL AND created_by = uid)
  ```

A plain `.eq("user_id", uid)` deletes exactly the rows the dual-source union exists to preserve — and note that a **zero production row count is not evidence the writer is safe**, only that no quick-call callback has been scheduled yet. - **A returned Supabase error is a FAILURE, never an empty result.** `{ data: [], error: null }` is a successful empty result meaning "none found". `error !== null` must reject the whole operation via `DashboardQueryError` (`assertNoQueryError`, exported from `dashboard-contact-identity.ts`). Every callback row branch, every exact-count branch, and all six contact-table lookups are checked. **Never return a partial page or a partial count** assembled from the branches that happened to succeed, and **never convert a failed contact lookup into a dangling/deleted identity** — that reports a live contact as removed. The user-facing message is generic; the raw Supabase error is retained as `cause` for `console.error` only and must never be rendered. UI states for loading / valid-empty / failure must be distinguishable, and a failure must never render the valid-empty message. A successful-but-empty lookup uses neutral wording ("No linked contact record is available") because it can also mean RLS does not expose the row — do not assert deletion.
- **Contact identity:** `src/lib/dashboard-contact-identity.ts` is the ONE resolver. `calls.id` and `campaign_leads.id` are **never** contact identities. An unknown `calls.contact_type` (NULL on most real rows, §5) resolves against the actual visible `leads`/`clients`/`recruits` rows; **ambiguous or unresolved ⇒ `null`, never a `lead` default**, and `null` disables the call and the navigation rather than routing to the Leads tab. A null or dangling `campaign_leads.lead_id` still renders and still counts, but cannot be acted on.
- **Browser-local calendar math:** `src/lib/local-calendar.ts` constructs calendar days (`new Date(y, m, d + n)`); never add `n * 86_400_000` to a local midnight, which breaks across DST. That module is **browser-local only** and is **not** the agency-timezone architecture (still Build 2).

Never apply an activity limit before authorization: `messages_select` is organization-wide, so another agent's traffic will otherwise crowd the viewer's own conversations out of the window. Query errors must THROW so the UI can offer a retry; `(x.data || [])` on a failed query renders a partial list as if it were complete.
- **Identity comes from `useAuth().profile` (already impersonation-aware), never `useAuth().user`.** Use `useEffectiveViewer()` / `EffectiveViewer`. **The organization-wide branch is decided by `isOrganizationWideViewer` — NEVER by `useOrganization().isSuperAdmin`, which is `isSuperAdmin || isImpersonating` and therefore `true` for the whole duration of a "View As" session.** Gating a data-scope branch on that flag widens "View As Agent" back to the entire organization. `isEffectiveSuperAdmin` is the safe replacement at data-scope sites; navigation/visibility gates may keep the old flag.
- **The effective `Profile` is built by ONE validated mapper, never a cast — and now only from a server row.** The camelCase `UserProfile` DTO has `userId`/`organizationId` and NO `id`, `role` or `organization_id`; the former `as unknown as Profile` cast at both entry points made every scoping field `undefined` and left `usePermissions` loading forever. `profileRowToImpersonationProfile` is the only mapper that may produce an active impersonation, it FAILS CLOSED (returns `null`) rather than yielding a half-built profile, and it never carries `platform_role` — platform authority is read from `realProfile`. **Superseded 2026-08-27 (second pass): `startImpersonation` no longer takes a `Profile` at all** — it takes the target's id and re-reads the row itself (see the direct-activation rule below). `toImpersonationProfile` remains exported and tested but is no longer on any authority path.
- 🚨 **"View As" is an AUTHORITY decision and `localStorage` is attacker-controlled — never hydrate authority from it (corrected 2026-08-27).** Storing the whole `Profile` and rehydrating it after a SHAPE-only check was a privilege-escalation bypass: any signed-in Agent could write `{ id, role: "Admin", organization_id }` into `agentflow_impersonation` and `useAuth().profile` would hand every scoping surface an organization-wide role. The rules now:
  - persist ONLY `{ version: 2, ownerProfileId, targetProfileId }` — two identifiers, nothing role-, org- or flag-bearing;
  - 🚨 **stored "View As" intent belongs to the OPERATOR who parked it, and must be bound to them (corrected 2026-08-27, fourth pass).** `localStorage` is scoped to the ORIGIN, not to the account. A v1 pointer recorded which target was chosen but not by whom, so operator X's parked intent outlived X signing out and was re-read as Y's the moment Y signed in on the same browser. Whether Y could act on it fell through to "is Y also a Super Admin in that organization" — a question the pointer had no business asking, because the intent was never addressed to Y at all. So: record `ownerProfileId` at write time, and restore only when it matches the REAL authenticated profile EXACTLY. Compare the owner **before the target is looked up** — a pointer that is not this operator's must not buy a `profiles` round-trip. Legacy payloads (v1, and the original full `Profile`) have no recoverable owner, and one cannot be inferred from whoever happens to be signed in now — that inference IS the defect — so both are rejected AND erased on sight, rather than salvaged;
  - activate impersonation ONLY after the REAL database-backed profile has loaded and proved `is_super_admin === true`, then RE-FETCH the target from `profiles` and validate it (present, not `Deleted`, has a scoping identity) **and explicitly check it is in the real account's `organization_id`** — do not let RLS stand in for that check (§3);
  - gate `startImpersonation` itself on the real profile's `is_super_admin`;
  - revoke a live impersonation the moment the real account stops being a Super Admin;
  - wrap every storage read/write/remove in `try/catch` and fail closed — a blocked or throwing store must neither crash nor enable impersonation;
  - 🚨 **direct activation must DERIVE the target's authority from the server — it must never require, or trust, a caller-supplied full `Profile` (corrected 2026-08-27, second pass).** Authenticating the real caller is only half the decision. `startImpersonation` used to map the caller's own object through `profileRowToImpersonationProfile`, so the TARGET's role, status, organization and super-admin flag all came from the argument: a candidate claiming `role: "Admin"` over a database row that says `role: "Agent"` produced an organization-wide effective viewer. The rules now:
    - `startImpersonation` reads **only the `id`** from its argument (a bare id, or any object carrying one) and is `async`, returning `Promise<boolean>`;
    - the REAL profile must prove `is_super_admin === true` and carry an `organization_id`;
    - the target is re-fetched from `profiles` with **both** `.eq("id", targetId)` **and** `.eq("organization_id", realProfile.organization_id)`, and **only that server row** is mapped;
    - the target must be an ELIGIBLE ACTIVE account — `status === "Active"` exactly, an allow-list, so `Inactive`, `Pending`, `Deleted`, an unrecognised value and a missing value are all refused (`isImpersonatableStatus`). Rejecting only `Deleted` let `Inactive` through, a status `fetchProfile` treats as grounds to sign the account OUT;
    - missing, malformed, self, foreign-organization and unreadable targets are refused, and a refusal writes NOTHING to storage;
    - the owner-bound pointer is stored only AFTER the server row validates, with the REAL profile's id as the owner;
    - callers `await` it and navigate only on a confirmed `true`.
    A check present on one entry point but not the other is not a check: the restore path applies the identical gates against the identical query.
  - 🚨 **SESSION IDENTITY is the root of the decision, and it changes one layer BELOW the profile authority is read from (added 2026-08-27, third pass).** `onAuthStateChange` awaits `fetchProfile` only for `INITIAL_SESSION`; every other event — `SIGNED_IN` above all — defers it through `setTimeout` to avoid a Supabase client deadlock. For that whole window the authenticated user is already B while the trusted profile is still A, so an in-flight activation started by A compared the profile to ITSELF, passed, and committed. Comparing a profile to a profile can never catch a session replacement. The rules:
    - record the authenticated user id SYNCHRONOUSLY the moment a session is adopted (`sessionUserIdRef`), before the new profile fetch is awaited OR scheduled;
    - on an identity change, destroy everything the previous identity authorised — real profile, live impersonation, pending restore target, persisted pointer — and bump a generation counter (`authorityGenRef`) that supersedes every in-flight attempt. A FIRST adoption authorised nothing, so it must not clear the pointer the page was loaded with: that is the legitimate restore path;
    - a profile fetch may apply its result only if its requested user is still the live session — otherwise a slow read for A lands after B took over and reinstates A;
    - both direct activation and stored-pointer restore capture session AND generation, and re-check both immediately before committing. A superseded RESTORE bails silently and drops its pending target, but must NOT clear storage: a newer activation may already own it, and leaving the pending target set makes the next profile change re-fire the whole restore;
    - the generation is bumped once a request is known to be well-formed and authorised — not on entry, or a stray self-click cancels a legitimate activation mid-flight;
    - `logout()` and `stopImpersonation()` express newer intent and bump it too.
    A counter is needed as well as an id comparison: A → B → A returns the session id to where it started, and only the counter records that an identity change happened at all.
  - 🚨 **`null` is not one state — an in-flight bootstrap needs an EPOCH, not another id comparison (added 2026-08-27, fourth pass).** `getSession()` answers with whatever session existed when it was CALLED, and the guard against a stale answer was `sessionUserIdRef.current !== null && !== bootstrapUserId`. But `sessionUserIdRef.current === null` means BOTH "the listener has not spoken yet" AND "the listener delivered `SIGNED_OUT`" — so after a sign-out the bootstrap read `null`, concluded nothing newer had happened, and re-adopted the user, session and profile of an account that had already left. No id comparison can fix that: the discriminator is not WHICH identity, it is WHETHER anything newer has spoken, which is a count. Keep an `authEventEpochRef`, bump it SYNCHRONOUSLY at the top of every auth callback (`SIGNED_OUT` included, and a repeat of the same identity included), capture it immediately before starting `getSession()`, and discard the bootstrap if it moved. A same-user `TOKEN_REFRESHED` still bumps it and still changes nothing else, so a live impersonation survives a refresh untouched.
  - 🚨 **`logout()` must revoke local authority BEFORE it awaits the remote sign-out (corrected 2026-08-27, fourth pass).** `signOut()` is a network round-trip, and tearing down after it left a window the length of that request in which the user had pressed "Log out" and the provider still held a live Super Admin profile, a live impersonation, an un-bumped generation and a stored pointer. An activation already in flight re-checked `realProfileRef` / `authorityGenRef`, found them exactly as it left them, and COMMITTED — installing a "View As" into a session the user had already ended, which the later teardown could not undo. Express intent the instant it is known: bump both counters, clear the identity, the real profile, the effective profile, the pending restore and stored intent, and only THEN await. **Fail closed if `signOut()` rejects** — nothing is rolled back, the error propagates so the caller can surface it, and this tab stays locally revoked. A test with an immediately-resolved `signOut()` mock cannot see this race; the mock must be genuinely deferred.
  - **Nulling the real profile has blast radius — check what else keys on it.** `isBuildingOrganization` is only ever reset inside `if (session?.user && profile?.organization_id && profile?.role)`, so making the profile null on every identity change latched it ON and made `AuthProvider` render "Loading your agency" INSTEAD of its children, blanking the whole application. Any effect that both sets and clears a flag inside the same truthiness guard needs an `else` that clears it.
  - 🚨 **"View As" is a READ-ONLY PREVIEW on an ALLOW-LIST of audited surfaces — it is not a global mode (added 2026-08-28).** Repairing the impersonation payload had a consequence nobody asked for: it turned "View As" ON everywhere. Before the repair the effective profile carried `organization_id: undefined`, so `usePermissions` never satisfied `canFetchPermissions` (`usePermissions.ts:151`) and latched `isLoading` — every impersonated page sat on a spinner and the blast radius was zero. Afterwards every route mounted and ran its queries under the viewed identity, including the ~20 written against `useAuth().user` (the REAL operator): `Dashboard.tsx` and `Reports.tsx` read `user?.id`, and Settings, the Dialer and the CSV import page can WRITE. The rules:
    - `src/lib/viewAsSurfaces.ts` is the ONE list. Phase A supports **Conversations**, and **Contacts limited to its Import History and Agents tabs** — the only surfaces whose full read path is proven to resolve from the effective viewer. Everything else is withheld pending a separate audit;
    - enforcement is at the LAYOUT (`AppLayout`), around `<Outlet />`, not in `PageGuard`. That covers direct URLs, `navigate()` and history alike, covers the routes carrying no `PageGuard` (`/settings`, `/agent-profile`, `/app-link/:linkId`), and makes it a MOUNT guarantee: the route element is never constructed, so its effects never run. A guard inside a page could only unmount it after its queries had fired;
    - match the pathname EXACTLY and case-insensitively. React Router matches routes case-insensitively, so `/DASHBOARD` reaches Dashboard; a prefix match on `/contacts` would admit `/contacts/import`;
    - LAYOUT CHILDREN are page components too. `FloatingDialer` (places calls, writes `calls` rows, resolves caller ID from the real Twilio identity) and `ReminderPopup` (reads and dismisses the real user's appointments) mount on every route, so an `<Outlet />`-only guard leaves them running for the whole session. Both stay unmounted while impersonating;
    - the sidebar advertises only supported destinations — including through the `permsLoading` branch, which deliberately fails OPEN to the full menu, and including the three Super-Admin entries, which `useOrganization().isSuperAdmin` (`isSuperAdmin || isImpersonating`) would otherwise reveal *because* the session is impersonating;
    - both entry points land on a SUPPORTED surface (`VIEW_AS_LANDING_PATH`), never `/dashboard`;
    - the banner and its "Exit View As" stay OUTSIDE the guarded area, so a blocked route is never a dead end.
  - 🚨 **A guard that stops the PAINT but not the REQUEST is not a fail-closed guard (added 2026-08-28).** `contactGridsBlockedByViewAs` suppressed the four Contacts grid renders and gated `fetchData` — and `fetchKanban` was left ungated, so the board's RPCs still ran against the real session user with only the result discarded. Gate the fetch AND the effect that schedules it. And withhold the control that reaches the blocked path: the table/Kanban toggle now disappears with the grids.
  - 🚨 **Contact-detail machinery is NOT tab-scoped, so a tab-scoped guard does not close it (added 2026-08-28).** `?contact=`, the legacy `?id=` and the `openContactId` navigation state all run on Import History and Agents — the two SUPPORTED tabs — so a lead deep link opened while impersonating still fired `leadsSupabaseApi.getById`, then the client and recruit fallbacks, and mounted `FullScreenContactView`. Lock the whole machinery for the session, and DISCARD the id rather than parking it: strip it from the URL, or it is handed to the `fetchData` fallbacks on the next dependency change and re-resolved the moment "View As" ends.
  - 🚨 **Under "View As", reads may stay, WRITES may not (added 2026-08-28).** Conversations refuses `handleSendMessage` BEFORE reading the session, the connected mailbox or the selected caller ID — every one of those credentials belongs to the real operator, and a send would deliver from the operator's address or number to a contact belonging to the viewed agent. Placing the refusal after the reads would still have fetched the operator's mailboxes while impersonating. Import History keeps its reads, retries and drill-in but loses Import CSV, Retry attachment and Undo Import; `AgentModal` loses its availability change, note composer and Call button.
  - **Ownership is the EFFECTIVE viewer, or nothing (added 2026-08-28).** `handleAddLead` used `meta?.assignToAgentId ?? user?.id ?? ""` — the REAL user as a fail-OPEN default. The modal normally supplies an assignee, so this was not routine mis-stamping; it was a silent substitution of the one identity that must never be assumed. Resolve an explicit assignee, else the effective viewer, else REFUSE. `handleAddClient` / `handleAddRecruit` already did this.
  - **An async handler in a `void (async () => …)()` needs a `catch`, not just a `finally` (added 2026-08-28).** `finally` clears the lock but can neither report the failure nor stop what follows, so a rejection becomes an unhandled rejection and the user sees a control silently revert. `TeamMembersTable`'s Impersonate handler now distinguishes a refusal ("you aren't allowed") from a crash ("something went wrong") — different problems with different next steps.
  ⚠️ This is a FRONTEND authority boundary. It stops the application from GRANTING an elevated role; it does not stop direct PostgREST reads, which remain governed by RLS.
- **Clear viewer-scoped data at RENDER time, never in a passive effect.** React's order is render → commit → layout effects → paint → passive effects, so an effect keyed on an identity clears ONE COMMIT TOO LATE: the previous viewer's rows are committed and painted first. Store state together with the key it was loaded for and read it back through a derived value (`useImportHistory`, `ConversationsSidebar`, `Conversations`, `ContactBriefView`, `ConversationThread` and the Contacts → Agents table all do this). A test that only `waitFor`s the cleared state cannot see the leak — capture the committed DOM from a sibling's `useLayoutEffect`, which runs after every commit and before any passive effect.
- **UNSTARTED is not EMPTY, and a stale response is not an answer (added 2026-08-27).** The same one-commit-too-late window makes a keyed surface report "no results" before its first request has even begun, so derive `loading` synchronously for a key that is about to fetch. Pair every keyed surface with a request-generation guard (`loadSeqRef` / `fetchSeqRef`): a response for a superseded key must commit nothing — not rows, not an error, not a cleared loading flag. Pass the key into the loader as an explicit ARGUMENT so realtime callbacks and post-send refreshes cannot be re-pointed at whatever key happens to be current when they fire.
- 🚨 **A generation guard must also reject a stale START, not just a stale FINISH (added 2026-08-27, second pass).** Rejecting a late response is only half of it. A realtime callback or a post-send refresh bound to the PREVIOUS key can still execute after the switch — a websocket callback already queued runs after effect cleanup, and a debounced one re-arms a timer on a closure nothing will clear. When it starts a request it bumps the SHARED sequence, so the CURRENT key's in-flight response fails its own check and is discarded: the surface is left loading forever with nothing outstanding. Hold the live key in a ref written in a **`useLayoutEffect`** (current for anything that runs after a commit, unlike a passive effect) and prove the bound key is still active **before starting anything** — for a debounced handler, both when the event ARRIVES and again when the timer FIRES, since a stale event would otherwise occupy the shared debounce slot and swallow a live one. `ConversationThread.activeContactRef` and `ConversationsSidebar.activeKeyRef` are the reference implementations.
- 🚨 **A send that did not happen must not be reported as one (added 2026-08-27).** `Conversations.handleSendMessage` resolved `undefined` on every failure path — expired session, no email address, no connected mailbox, no phone number, no caller ID, a provider `success: false`, a thrown request — exactly as it did on success. `ConversationThread` awaited it and cleared the composer, so a failed send DESTROYED the user's message and left them nothing to retry. An operation whose failure the caller must act on returns an explicit result: `Promise<boolean>`, `true` only after a confirmed provider success, and the composer cleared and the thread refreshed on `true` and on nothing else. A mock that resolves `undefined` silently skips that whole path, so test doubles must honour the contract too. `void`-returning "it either worked or it toasted" handlers are the anti-pattern.
- **Reset every piece of per-identity UI state, not just the data (added 2026-08-27).** A composer draft, an email subject, the selected compose channel and the expanded-row maps are all contact-specific. A draft written for one person must never be one click away from being sent to another, so key them by contact AND clear them on the switch — keying alone resurrects a draft when the user returns, but only if they typed nothing in between, which is worse than either consistent behaviour. And when a test mocks the component that owns those props, the mock must match the REAL prop contract: the previous "draft is not carried across contacts" test mocked `MessageComposePanel` with `value`/`onChange`, props it does not accept, so nothing was ever bound and the test could not fail.
- **Subscribe to everything you READ (added 2026-08-27).** `getConversationThread` reads SMS with `.or(lead_id.eq.X, contact_id.eq.X)`, but the thread subscribed to `lead_id` alone — so a converted client, whose messages carry `contact_id`, never saw a new SMS appear. A realtime subscription that covers less than its query silently stops refreshing for exactly the rows the query was widened to catch. Register one FILTERED handler per link column rather than one unfiltered handler (an unfiltered `messages` subscription wakes every open thread on every SMS in the organization, because that RLS is organization-wide), and coalesce them so a row matching both filters causes ONE reload.
- **No silent truncation, and no pre-authorization cap.** Import History is PAGINATED with a visible "Load more" (`IMPORT_HISTORY_PAGE_SIZE` is a page size, not a ceiling). Conversations resolves the viewer's AUTHORIZED contacts first and constrains every activity query to that id set, so organization-wide traffic cannot occupy the window; an organization-wide viewer instead sweeps activity with an EXPLICIT `organization_id` filter. Where a bound genuinely exists it THROWS a user-visible error rather than logging a console warning behind a plausible-looking short list. Realtime sidebar reloads are debounced — `messages` RLS is organization-wide, so every org SMS notifies every agent.
- **Paging exhaustion is a property of the QUERY, never of the mapping (added 2026-08-27, second pass).** `read()` mapped rows to candidates and returned only the mapped array, and both sweep loops used that length as the raw page size. `messages.contact_id` and `messages.lead_id` are BOTH nullable (the legacy `lead_id` FK is `ON DELETE SET NULL`), as is `contact_emails.contact_id`, so a full 200-row page can map to ZERO candidates — read as "the table is exhausted", ending the sweep one page short of a real conversation. A source page therefore carries `{ rows, rawCount }` and every `=== 0` / `< PAGE_SIZE` comparison uses `rawCount`. Raw cardinality drives PAGING only: an unlinked row must still never surface as a conversation.
- **When several independently-ordered sources are merged, termination must be proved PER SOURCE (added 2026-08-27).** A source may stop only once IT has enough distinct resolved results of its own, exhausts its own rows, or reaches a surfaced reliability boundary. Counting progress across the shared result array lets a busy source settle a quiet one: an SMS-heavy tenant stopped the inbound-email sweep after a single page — a page that could be entirely orphaned contacts — and email-only conversations disappeared. A source that another source fully covers must be SKIPPED explicitly, not made to return an empty page that reads as "exhausted".
- **Query fan-out is a decision, so PIN it (added 2026-08-27).** `ACTIVITY_QUERY_BUDGET` states the source count, organization-sweep source count, page size, contact batch size and both page budgets, and tests assert every one of them — adding a source or widening a page fails a test instead of quietly multiplying every load. A bounded single-row lookup must genuinely request one row; describing a full-page read as a `.limit(1)` fallback in a comment is not a bound. Collapsing this fan-out into a database view or RPC is Phase B, after S1.
- **A request that can reject needs a `.catch`, a request generation, and a key — all three (added 2026-08-27).** `ViewAsModal`'s user list had none: a rejected `getAll()` left `loading` true forever, so the modal span forever with no error and no retry. Every fetch-backed surface needs the same three things — an error state distinct from the empty state, a sequence guard so a stale response cannot repaint the current view, and a key that distinguishes one OPEN from the next (reusing it repaints the previous open's error, or a row for a user since deactivated, while a fresh request is still in flight). Bump that key on CLOSE, not on open, or every open fires two requests. And any in-flight lock cleared in a `finally` must ALSO be reset when the surface reopens: a round-trip that never settles otherwise disables every row for the rest of the session.
- **Import History is organization-scoped AND uploader-scoped.** Admin / non-impersonating Super Admin see the whole effective organization; **every other role, Team Leaders included, see only `agent_id = effective profile id`** (the downline is deliberately not consulted). `organization_id` is always present. Fetch only while the Import History tab is active, clear on a viewer change, guard stale responses with a request generation, and keep an error state distinct from the empty state.
- **Impersonation cannot change the DATABASE ACTOR, so RPCs whose scope derives from `auth.uid()` FAIL CLOSED (wording corrected 2026-08-28).** These were previously described here as `SECURITY DEFINER`; they are not. `supabase/migrations/20260806000000_baseline_production_schema.sql` defines `get_contact_scope_agents` (:2320) and `search_contacts_leads` / `_clients` / `_recruits` (:5339/:5363/:5421) as `LANGUAGE sql STABLE` with no `SECURITY DEFINER` clause — i.e. PostgreSQL's default **security-invoker** behaviour. The limitation is not the security mode: it is that "View As" is a CLIENT-side swap of `useAuth().profile` and cannot change the JWT or the database actor, so any predicate or input derived from the real authenticated session (`auth.uid()`, `get_org_id()`, `is_ancestor_of(auth.uid(), …)`) still resolves to the real Super Admin. `get_contact_scope_agents` hard-codes `p.id = auth.uid() OR public.is_ancestor_of(auth.uid(), p.id)` in its body, so impersonation is invisible to it. Under "View As" the Contacts Leads/Clients/Recruits grids are therefore withheld with an explanation (they would show the Super Admin's own book of business under the viewed user's name), `useContactScope` returns no team agents, and no scope preference is persisted. Import History and the Contacts → Agents tab are unaffected — both are scoped client-side against the effective profile.
- **This is QUERY SCOPING, not a database authorization boundary** (AGENT_RULES §3). `messages_select` and `import_history_select` remain organization-wide (`organization_id = get_user_org_id()`); a determined user still reads them over PostgREST. Tightening either is a separate RLS phase requiring `#APPROVE_RLS_CHANGE` **and** separate remote-apply approval, **after** S1.

| Contact field layout resolution | User layout (`user_preferences.settings.contact_field_layout` per type) → agency default (`contact_management_settings.field_order_<type>`) → system default (`getDefaultFieldOrder` in `src/lib/contactFieldLayout.ts`). User layout overrides agency default; agency default applies to users who have not customized their own layout. Custom field IDs are stored as `custom:<name>`. |
| Required-field enforcement | Application/service-layer validation only. `contact_management_settings.required_fields_<type>` plus `custom_fields.required` are validated in frontend save paths (Add/Edit Lead/Client/Recruit, FullScreenContactView) and in `import-contacts` (core fields only). Business-required columns are **not** enforced via DB `NOT NULL`. |
| **Client policy columns** (Contacts Build 1, 2026-06-17) | Canonical: **`clients.premium`** (numeric), **`clients.face_amount`** (numeric), **`clients.issue_date`** / **`clients.effective_date`** (text `YYYY-MM-DD`, blank → `NULL`). **`clients.premium_amount` is deferred schema debt — never write it** (don't drop/rename/backfill it either). Manual Client CRUD (`supabase-clients.ts` `rowToClient`/`clientToRow`/`update`) must use the **same columns as `conversionSupabaseApi.convertLeadToClient`**. Display: missing/zero premium & face → blank/`—` (**never a fabricated `$0`**); missing issue/effective dates → blank (**never substitute `created_at`**). Blank optional values persist as `NULL`, not `0`. |
| **Contacts Last Disposition** (Contacts Build 1, 2026-06-17) | The Contacts/Leads "Last Disposition" derives from **`calls.disposition_id`** / trimmed **`calls.disposition_name`** of the newest *dispositioned* call (`deriveLastDisposition` in `supabase-contacts.ts`) — **NEVER `calls.status`** (that's telephony status). A call with neither disposition field is not a disposition. Filter matching normalizes (trim + lowercase, `normalizeDispositionValue`) so options align with stored values; legacy `disposition_name`-only rows still match. (Mirrors the trusted-Contacted prefer-id/fallback-name rule, invariant #13.) |
| **Manual contact ownership** (Contacts Build 1, 2026-06-17) | New Client/Recruit require an authenticated `user.id` **and** `organization_id` — **no `u1` fallback**; block the save with an error on missing context. `clientsSupabaseApi.create` / `recruitsSupabaseApi.create` throw without `organizationId`. Bulk assignment persists **before** clearing selection: Leads write `assigned_agent_id` **and** `user_id` (RLS sync); Clients/Recruits write `assigned_agent_id`. On failure keep the selection + prior ownership (no fake success). Assign targets limited to the viewer-authorized set; **select-all-leads disables Assign** (deferred to Build 2). `getById` on leads/clients/recruits uses `.maybeSingle()` and returns a not-found error — never map `null`. |
| **`calls.contact_type` is often NULL for lead calls** (Contacts Build 2, 2026-06-19) | The Dialer writers (`dialer-api.createCall`/`saveCall`) put the contact's id in **`calls.contact_id`** but persist **`contact_type` as `contact_type \|\| null`** — so most real lead calls have `contact_type = NULL` (and **`calls.lead_id` has no current writer** → 0 populated in prod). Any code linking calls→leads must use the **compatibility relation**: `c.lead_id = l.id OR (c.lead_id IS NULL AND c.contact_id = l.id AND (c.contact_type = 'lead' OR c.contact_type IS NULL))` — **never** a strict `contact_type = 'lead'` (matches 0 real rows) and **never** a PostgREST `!inner` embed-order for agent sorting (drops unassigned). The Contacts attempt-count + Last-Disposition RPCs (`_contacts_filtered_leads` / `search_contacts_leads`, migration `20260619180000`) use this. **Open follow-up:** normalize the call writers to consistently set `contact_type='lead'` (telephony change — needs its own review for telemetry/calling impact); after that the fallback may tighten to `= 'lead'`. |
| **Conversion lineage — `clients.lead_id` + `call_logs.lead_id` are LINEAGE, not live FKs** (Contacts Build 3 CP4, migration `20260620000200`) | Lead→Client conversion goes through ONE atomic RPC `public.convert_lead_to_client_atomic(p_lead_id, p_client)` (SECURITY DEFINER; auth via `auth.uid()`+`get_org_id()`; idempotent on `clients.lead_id`). The migration **drops `clients_lead_id_fkey` and `call_logs_lead_id_fkey`** (both were ON DELETE SET NULL) so those `lead_id` columns survive the lead delete as **immutable source-lead lineage** (partial-unique on `clients.lead_id`; index on `call_logs.lead_id`). **Never** treat `clients.lead_id`/`call_logs.lead_id` as a live FK or re-add the FK. Conversion **moves** the polymorphic contact graph (notes/activities/appointments[contact_id-only]/tasks/calls/messages/contact_emails/workflow_executions) to the client and **preserves telemetry** (never deletes/rewrites `calls`/`call_logs` duration/recording/disposition/provider/campaign ids; `campaign_leads` untouched — Dialer lock/advance/disposition unchanged). **Never write `clients.premium_amount`.** Conversion wins are DB-idempotent via `wins.idempotency_key='conversion:<lead-id>'` (created after commit; celebration failure never rolls back the client). |

## 6. Dialer Model

**Single-leg WebRTC only.**

1. `TwilioContext.makeCall()` → guards → insert `calls` row.
2. `twilioMakeCall()` → `device.connect({ params: { To, CallerId, CallRowId, OrgId } })`.
3. Webhooks update `calls`; inbound via `twilio-voice-inbound` + `inbound-call-claim`.

Do **not** reintroduce server REST outbound + SIP bridge (`dialer-start-call`) unless Chris explicitly requests it.
