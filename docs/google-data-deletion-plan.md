# Google data deletion and backup verification — review build

Prepared September 22, 2026 for Christopher Garness. **Chris approved the Gmail-only implementation with “Proceed.” It is now implemented and locally tested in draft PR #378; it is not deployed. No production deletion, migration, deployment or backup change has been executed.** The historical proposal below records scope; the implemented contract and operator steps in this section take precedence.

## Implemented Gmail contract

- Migration `20260922055909_google_data_deletion_requests.sql` adds a service-only RLS request ledger, a pending-deletion barrier and generation provenance for new Google messages. Request rows deliberately have no cascading profile/org FK. A profile lock serializes connection transitions, writes and erasure. Browser users cannot call the new functions or read the ledger. Existing Google-derived content is immutable except contact reassignment, connection detachment and notification read/dismiss controls.
- `google_mailbox_deletion_manifest` is read-only: one org/user/mailbox, exact IDs for messages, matching notifications (including leadership recipients) and attributed send activities. Each category is capped at 10,000 IDs; any excess blocks execution. It exposes no bodies, subjects or tokens. Gaps block execution, including inferred legacy mailbox sources, unknown sources, unlinked send activities and orphan inbound notifications anywhere in the agency. This conservative organization-wide notification check can require review of an unrelated orphan before proceeding; it never broadens erasure scope.
- `begin_google_mailbox_deletion` checks the reviewed manifest again under the lifecycle lock, records the verified request/deadline/operator/external-ledger reference, cancels pending email OAuth states and clears the selected mailbox's credentials/cursors. Deleting detached old-account history preserves the replacement account's connection. No Google revoke or remote mailbox-delete call occurs.
- `erase_google_mailbox_batch` deletes at most 500 rows per category per transaction. It removes attributable notifications/activities before their messages, keeps counters, verifies remaining scope and leaves the barrier pending on failure. The same request resumes idempotently; a completed request never erases data imported by later fresh consent. A deliberate reconnect after completion requires a new OAuth flow.
- Outbound message/history activity writes are atomic and include per-message provenance. Inbound previews use a guarded RPC. Database triggers reject obsolete direct workers and delayed derived copies. A network send already dispatched to Google cannot be recalled; the endpoint reports successful acceptance separately from local-history failure.
- `scripts/delete-google-mailbox-data.ts` defaults to dry-run. Execution pins the exact Supabase project, request, reviewed manifest SHA-256 and an operator-attested durable external ledger. It flushes a write-ahead ledger record before beginning deletion and appends each batch result. Only counts/status appear on stdout. An attestation/environment flag is **not independent evidence of durability**; the actual destination, access and restore process must be verified before any real request.
- Completion is `live_deleted` for the covered database rows. Other-copy review remains pending; Google grant revocation is not claimed. Gmail local erasure does not require revoking Calendar's shared grant. Use the existing explicit Remove Google access control separately when requested, or Google's account controls if credentials are unavailable.

### Evidence that affects deployment

Read-only production catalog inspection found only updated-at triggers on the email tables, no message FK on notifications/activities, lead-conversion `contact_id` reassignment, and a contact-email existence check in import undo. Those are preserved; the broad organization wipe remains unused. The system workflow email writer uses Resend, outside this Gmail scope. Existing production aggregate counts were 233 Gmail messages (none detached), zero inbound notifications missing event keys and one legacy Google-send activity without a message ID. No content/credential values were read. The new provenance column is not deployed; existing messages will require a separately reviewed provenance remediation before this tool can erase them. Never manufacture a generation value or disable guards to clear a blocker. A backfilled current mailbox label alone does not prove historical source after account switching.

### Operator procedure (not executed)

1. Deploy the reviewed migrations and all compatible writers under the runbook's approved maintenance process. Validate real concurrent workers in staging; PGlite tests cover ordered stale-worker interleavings, not production concurrency or a real backup restore.
2. Verify requester/authority, scope, holds and deadline. Prepare a private JSON request with `project_ref`, UUID `id`, `organization_id`, `user_id`, normalized `mailbox`, ISO UTC `received_at`, `verified_at`, `due_at` (no later than 30 days after verification), `authority_ref`, `operator_ref`, `ledger_ref`, and `holds_reviewed: true`. References point to restricted evidence; do not put request correspondence or inbox content in the JSON. Deadline tracking is operator-run; no reminder scheduler or automatic SLA enforcement is added.
3. Supply `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` privately. Dry-run: `deno run <scoped permissions> scripts/delete-google-mailbox-data.ts --request <private-request.json> --manifest <new-private-manifest.json>`. Review counts, IDs, provenance gaps, other copies and recovery implications. The new manifest is created exclusively with mode 0600; existing files are not overwritten. Oversized/ambiguous requests require a new specific review, not a wider delete.
4. Obtain approval of the exact request/manifest hash and operation. Establish a restricted durable ledger **outside the Supabase restore boundary**, verify access/retention/recovery, and set `GOOGLE_DELETION_LEDGER_READY=true` only after that check. Execute the same command with `--execute --approved-sha256 <reviewed-hash> --ledger-dir <verified-directory>`. Limit Deno network access to the approved host and file access to those private locations. No production command is approved by this document.
5. If interrupted, retain the pending barrier and resume the same request/hash. A stale manifest before begin fails without disconnecting. After a committed begin, failures retain the barrier. Do not reset status manually or roll back to old writers. Verify completion counters and scope, then separately handle provider logs/exports/Storage/manual copies and backup expiry before confirming all-copy deletion.
6. Before reopening a restored environment, disable access/sync, recover the independent ledger, reconcile pending and completed requests, and generate fresh inventories for the restored records. Each replay uses a new reviewed request ID linked to the original authority reference; the original completed ID intentionally cannot delete later-consent data. Resolve restored legacy provenance rather than bypassing it. Replay/verify before restoring access. The synthetic replay test is not proof of an operational external ledger or hosted restore.

Current limits: no self-service erasure UI, broad account removal, Calendar event erasure, agency export/closure, automated backup expiry or configured external ledger. These remain release gates for broader policy commitments.

There were no FKs targeting appointments in the inspected catalog; polymorphic references and trigger-driven dependencies still need their own review.

## Proposed scope and data inventory

First implement a verified, operator-run **Gmail data deletion request** with a mandatory dry-run and an independently approved execution. It must not become a generic agency wipe or delete anything in the user's Google mailbox. Calendar data deletion, departing-agent access removal and workspace closure/export need the additional inventories below before implementation.

| Data | Local source evidence | Required treatment |
| --- | --- | --- |
| `user_email_connections` | OAuth and email consumers | Match organization, user and Google provider. Stop sync, rotate generation, clear credentials and pending work before deletion. Preserve enough non-secret identity to prevent stale restoration. |
| `email_oauth_states`, `email_sync_cursors` | Expansion migration and shared OAuth lifecycle | Cancel the selected user's relevant pending state/cursor records. Do not affect another user's authorization. |
| `contact_emails` | Email send/sync handlers | Scope by organization + `owner_user_id` + provider + verified source mailbox, including history detached from `connection_id` after an account switch. Legacy source ambiguity is a manual-review blocker, never permission for a broad delete. |
| `notifications` | `insertInboundEmailNotifications`, `inboundEmailEventKey` | Match the selected message IDs through `event_key='inbound_email:<id>'` and organization. These notifications may belong to leadership recipients. Erase their subject/body snippets as part of the covered data; legacy rows without provenance require review. |
| `activity_logs` | Email-send activity insert | Select only attributable Google email activities using organization, user and metadata. Current metadata lacks a per-message ID; add future provenance and review legacy records without deleting unrelated agency audit history. |
| `calendar_integrations`, `appointments` | Calendar consumers | Inventory separately. Google imports can overwrite fields of linked appointments; `sync_source='external'` alone does not prove a record was originally created by Google. Preserve unrelated CRM appointments and do not delete Google events as a side effect of local erasure. |
| Storage, logs, exports and backups | Not established by inspected email handlers | Inspect bucket metadata, all active writers/processors, application logs, manual dumps, replicas, provider copies and export destinations. No absence claim without checking them. |

Before implementing SQL, perform read-only catalog inspection for these tables' columns, constraints, foreign keys, triggers, grants and RLS, plus dependencies referencing them. Query counts/provenance completeness only; do not retrieve private message bodies or credential values. Record the exact resolved dependencies in this plan before adding any additional table to a deletion operation.

## Request and completion contract

1. Verify the requester's identity and authority, exact agency/user/mailbox, covered data and any specific retention obligation. Agency ownership does not automatically authorize disclosure of another agent's private mailbox data.
2. Record the received/verified dates, deadline and owner. Use the approved target of 30 calendar days after verification, sooner where required. Record any hold with its reason, exact coverage and next review; do not silently extend a deadline.
3. Stop the affected integration and establish a durable barrier checked at every persistence point. Invalidate pending OAuth state and stale connection generations. Shared Google-grant revocation affects Calendar too and must be disclosed and reconciled.
4. Generate a bounded manifest with counts, row identities, provenance gaps and dependency effects. Obtain approval of this concrete operation. Store the manifest securely outside chat and avoid subjects, bodies, tokens or unnecessary addresses in audit output.
5. Execute in idempotent bounded transactions, verify zero covered live rows and no delayed reinsertion, and record failures honestly. Preserve unrelated clients, calls, policies, agency records and other users' copies.
6. Confirm live deletion separately from backup expiry. Keep a minimal restricted deletion ledger that survives restoration; before reopening access or restarting sync after a restore, replay completed erasure requests against restored data. Do not claim completion of all copies while backup evidence is missing.
