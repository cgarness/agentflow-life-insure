### 3.3 KPI envelope, rules and truth table (main §2.2)

```
{ id, value,                                        -- number | null
  status: 'available' | 'partial' | 'unavailable',  -- evidence completeness of value
  reason: <registry code> | null,                   -- primary reason; null iff status = available
  numerator, denominator,                           -- exact integers (or exact cents) for ratios and rates
  coverage: { eligible, assessable, unassessable, reasons: { <code>: int } } | null,
  maturity: null | { window_days: 30, state: 'complete' | 'in_progress',
                     members, pending, successes_to_date,
                     mature_members, mature_successes, fully_mature_on },
  detail: object | null }
```

`private.report_v3_metric` and the Zod superRefine in `src/lib/reports-v3-schemas.ts` enforce the same rules. A violation raises P0001 and fails only that panel, closed.

1. **Status describes evidence; maturity describes pending outcomes.** They are independent. A KPI can be partial and in progress at the same time.
2. **unavailable** ⇒ `value` is null and `reason` is non-null. The reason is one of:
   - a config code;
   - a zero code, when the KPI's denominator (or, for count KPIs, its population) is genuinely empty and nothing is unassessable;
   - a coverage code, when the side that decides the value has no known items but has unknown ones: `coverage.assessable = 0`, or a known denominator of 0 with `coverage.unassessable > 0` (BC4).

   Fixtures (X3): KPI 1/4 with every premium invalid → `premium_invalid`; KPI 17 with no resolved outcome → `outcomes_unresolved`; KPI 12/18 with every member unresolved → `attribution_unresolved`.
3. **partial** ⇒ `value` non-null and `reason` a coverage code. Coverage is non-null with `unassessable > 0`, or a **window-level** condition applies. These allow Partial without per-item unassessable counts:
   - `outcome_capture_partial_period`: the window straddles capture start;
   - `capture_gap` for a disabled-capture interval, and for KPI 15 bookings whose capture failed. Such a booking is counted from its receipt or current row and classified like a legacy row; for KPIs 16–18, gap items stay unassessable (RL-42);
   - `history_incomplete` from numberless unresolved calls (§2.11);
   - `legacy_booking_basis`: legacy-classified bookings are **counted**, with the basis disclosed. A window made only of legacy rows is therefore Partial, not unavailable.

   A window-level condition's count lives in `coverage.reasons[<code>]`, with `coverage.unassessable` left at 0. For KPI 15, `detail.basis_counts.legacy` mirrors `coverage.reasons.legacy_booking_basis`.
4. **available** ⇒ `value` non-null, `reason` null, and coverage null or `unassessable = 0`.
5. **Values never erase evidence states.** A numerator of 0 over a positive denominator gives `value = 0` under whatever status the coverage implies. A count KPI on an empty window is `available 0` only when its evidence for the window is complete: KPI 15 before PKG-D is `unavailable/evidence_not_captured`, not 0. KPI 1 with no policies is available at $0.00.
6. **Zero values come from complete evidence only (BC4).** Each KPI is judged on its own numerator and denominator, as defined in the truth table below. A genuinely complete zero numerator over a positive denominator is a valid 0. Missing numerator evidence is never turned into 0, and a zero denominator never yields a ratio.
7. **Maturity** applies only to the 30-day group KPIs 12, 18 and 19. The `maturity` block is present whenever the cohort has members, **including when the value is unavailable**, so known pending-outcome metadata is never discarded (BC4). The one exception is a config reason: no cohort is read (or, for `journey_scope_restricted`, none is disclosed), so the block is null.
   - Success means Sold Date − anchor agency date ∈ [0, 30]. Outcomes after the period end count.
   - A member matures at `private.report_v3_local_day_start(anchor + 31, tz)`. `pending` counts members not yet mature.
   - `state = 'in_progress'` iff `pending > 0`. `fully_mature_on` = max anchor + 31 (agency date).
   - **`value` is the observed result to date over the same assessable cohort.** Pending members stay in the denominator (18, 19) or the numerator (12), and no early successes are selected. A first-contact prospect who has not bought is a valid member: pending until mature, then a non-success.
   - `mature_members` and `mature_successes` count only members whose window has elapsed. They are never mixed with immature successes. This mature-only subset appears in details and in the CSV under its own column names, never as a second rate under the metric's name.
   - **Whole group.** `members`, `pending`, `mature_members` and `fully_mature_on` count every group member, assessable or not, so the block survives an unavailable value. `successes_to_date` and `mature_successes` count only verified successes. When unassessable members exist, the mature-only subset is therefore a lower bound, and the details say so (copy reviewed with the PKG-F preview).
   - **Block invariants** (enforced by `private.report_v3_metric` and Zod): `mature_members + pending = members`; `mature_successes ≤ successes_to_date`; for 18 and 19, `successes_to_date ≤ members` and `mature_successes ≤ mature_members` (12 counts policies, which can exceed members); `state = 'in_progress'` iff `pending > 0`; `fully_mature_on` is non-null.
   - ★2 is decided: observed-to-date is the primary value, with a compact In progress status and mature-only details on demand.
8. **Reason precedence.** `reason` is the first applicable code in registry order (config, then zero, then coverage). `coverage.reasons` carries counts for every applicable coverage code.
9. **Coverage.** `assessable + unassessable = eligible`. Coverage describes the side whose unknown items decide the status (the "Unknown parts" column below); its population is in the metric registry (§3.5). For KPI 7: eligible = contacted calls excluding recruit-resolved calls; assessable = resolved lead/client; unassessable = unresolved (X18).
10. **Precision** (§2.5). The builder keeps `value` at full precision (scale ≤ 6) next to exact `numerator` and `denominator`. It never rounds a value that the client rounds again. Ratios are built from combined counts and never averaged across agents.
11. **No panel raises** on fixtures with unresolved identities, unverified calls, unresolved appointments, empty windows or open windows.

**Status truth table (BC4).** For each KPI, **N** is the numerator (or the count or sum) and **D** is the denominator. Each side has a known part and an unknown part (unassessable items that could change it). Every reader evaluates each KPI in this order and stops at the first match:
1. any applicable **config** code → `unavailable`;
2. **denominator** (ratios, percentages, medians):
   - D known = 0 and D unknown = 0 → `unavailable` with the zero code;
   - D known = 0 and D unknown > 0 → `unavailable` with the first applicable coverage code.
   - KPIs 1 and 4 override this when policies > 0 but no premium is usable: `premium_invalid` if any premium is invalid, else `premium_not_entered`;
3. **numerator** (and count or sum KPIs): N known = 0 and N unknown > 0 → `unavailable` with the first applicable coverage code. A fabricated exact zero is never shown;
4. any unknown part > 0, or a window-level condition (rule 3) → `partial`, with the value computed over the known parts;
5. otherwise `available`. A complete 0 is a valid value.

The maturity block is attached for 12, 18 and 19 whenever members > 0, whatever the status.

For 12, 17 and 18, gap and unclassified items are candidates that could be sales appointments. A zero code (`no_held_sales_appointments`, `no_due_sales_appointments`, `no_attributed_policies`) therefore needs no known item **and** no candidate; otherwise the first applicable coverage code is used (rule 2).

### 3.7 Privacy contract (main §2.9; R04, BC1; ★1 pending, proposed design)

**Definitions.**
- An identity is *in scope* for a payload when it has at least one event credited to an in-scope agent that enters any of that payload's populations.
- An identity is *unrelated* when it has no event credited to an in-scope agent at any time.
- Cross-organization rows are never read.

**S14a, unrelated identities.** Adding any activity on unrelated identities leaves every personal and team payload of every reader byte-identical apart from `as_of`. This covers, by out-of-scope agents:
- calls of every attempt class, contacted calls and unresolved calls;
- sales, appointments, outcomes and attributions;
- links and state changes.

The same holds when matching activity is added in another organization.

**BC1 additions to S14a.** These must also leave every personal and team value, status, coverage block and reason code unchanged; they may change only unfiltered agency-scope diagnostics:
- adding or removing an unrelated out-of-scope **numberless** unresolved call;
- adding or removing unrelated unresolved activity elsewhere in the organization while an in-scope person has a captured phone change.

Organization-wide unknown-history diagnostics appear only at authorized, unfiltered agency scope.

**S14b, linked in-scope identities.** Activity by out-of-scope agents on an in-scope identity may change a scoped payload **only** through these aggregate effects, each subject to the option chosen in ★1.

| Effect | KPIs | What may change |
|---|---|---|
| E1 earlier contact or sale | 14, 19, 21, 38 | An earlier contact or sale by an out-of-scope agent removes the person from an in-scope first-contact or first-time-buyer population, or makes their 1 Call Close "No" |
| E2 earlier attempts | 21 | Out-of-scope outbound attempts before the person's first contact count in that person's attempt count |
| E3 purchase from anyone | 19, 18, 12 | A purchase from any seller within 30 days on the same identity counts as a success or an attributed policy. For 12 and 18, an eligible purchase that is not linked leaves the member unresolved, and one linked to another appointment resolves it as no sale |
| E4 recorded state | Regional | The in-scope event is grouped by the identity's current recorded state, whoever set it, including a campaign-membership copy reached through any same-org call on that identity (applies under every option) |
| E5 possibly related unlinked call | 19, 21, 38 coverage (never 14) | Member-specific evidence only. An unresolved call by any agent whose recorded number equals a number recorded for the in-scope member, placed before the member's anchor, makes that member unassessable for the KPIs whose gate it touches (§2.11): 19 only if the call could have qualified as a contact; 21 for any call; 38 only if it could have qualified before the linked sale call. A captured phone change on the member's own record counts the same way, whoever made it. Nothing is attributed to the person. Numberless calls and other members' activity are **not** E5 effects; they never change personal or team results (BC1) |
| E6 lead assignment | Lead-source breakdown "New leads" | New leads counts leads currently assigned to in-scope agents (the v2 rule, unchanged), so a reassignment by anyone changes it |

Never exposed in any option:
- row identities, phone numbers, timestamps or other agents' records;
- out-of-scope agents' names or rows (`by_agent` stays within scope);
- names or metadata of campaigns not visible to the viewer;
- an unattributed bucket below agency scope;
- cross-organization data.

Coverage counts and `unresolved_activity` count only in-scope credited items. Org-level values, including organization-wide unknown-history diagnostics, appear only at authorized, unfiltered agency scope (`agent_ids IS NULL`).

Numberless unresolved calls are not an E5 effect. At unfiltered agency scope only, they make KPIs 19, 21 and 38 `partial/history_incomplete` (a window-level condition), with the org-level count in `detail.history.numberless_unresolved_calls`. At personal and team scope, and with an agent filter, they have no effect (BC1). A captured phone change is evidence about the member's own record and never depends on other activity in the organization.

Implementation points that hold under every option:
1. Each population is credit-scoped: the original seller of the first sale for 14/38, the first-contact agent for 19/21, the assigned agent at the scheduled start for 12/18 (with none, no individual credit; agency totals only, BC3).
2. History may be org-wide inside SECURITY DEFINER, only to classify the in-scope credited population. It is read through window-bounded candidates and identity-keyed lookups (§3.11).
3. Output is aggregates only. Reasons that point at other agents' activity fold into the generic No or unclassified result.
4. D4's KPIs 12/18 pass `p_agents NULL` to `report_v3_sale_facts` (E3). D5's S2/S3 state lookups are in the review scope (E4).

**Tests in both directions** (`reports_v3_security.sql`; D2, D3, D4 and D5 add their legs):
1. For each of E1–E6, a fixture asserts the exact expected change and that nothing else changes: no new `by_agent` rows, no ids or names, no other KPI.
2. Removing the activity restores the original payload byte-identically.
3. A negative fixture covers out-of-scope activity of a kind not listed on an in-scope identity: calls after the anchor, appointments, purchases outside 30 days. The payload must stay unchanged.

**Filtered comparisons.** A viewer can difference adjacent windows or agent filters and so isolate one person's linked effect. Aggregation and minimum cohort sizes do not prevent this.
- Option (a), the proposed default, would accept that for the effects above (E1–E6), within the viewer's own credited population.
- Option (b′) allows personal and team scope only for whole agency calendar months with an in-scope denominator ≥ 5, else `journey_scope_restricted`. It narrows differencing but does not eliminate it.
- Option (c) removes E1–E3 and E5 below agency scope (E4 and E6 stay, because they are not journey effects): personal and team scopes return `unavailable/journey_scope_restricted` for KPIs 12, 14, 18, 19, 21 and 38.

The chosen option is a pinned constant in the journey and sales-appointments readers.

★1 remains open. The linked-history design is developed only as a clearly marked **proposed** design, in isolation and with BC1/BC2 applied. Production acceptance of these disclosures and the named security review of the exact SQL are pending. No reviewer has been appointed.

**Review gate.** A named security reviewer reviews the actual SQL of every reader body and the permission test results (S1–S15, including S14a/S14b) on the exact commit, before the reader bodies are frozen and before the PKG-A production approval. The review must also confirm E4's campaign-membership copy path, which an out-of-scope agent's same-org call can reach. The sign-off is recorded in `production-release.md`. ### 3.11 Indexes and performance gate (main §2.7)

Journey facts (D3) are computed in two phases:
1. Candidates come from window-bounded rows: journey contacts in [start_at, end_at) via `performance_calls_org_date`, plus first-sale candidates from the sold window.
2. History comes from identity-keyed lookups: `contact_history_calls_page` (contact_id), the new campaign_lead index, wins by contact, lineage by `original_lead_id`, and D3's §2.11 number check.

The four call readers reuse the window-bounded `report_v3_call_facts`. The redundant contact_id index was dropped from the plan.

> **Batch 6 clarification (2026-11-02): access paths, not semantics.**
> - The call rows of `report_v3_call_facts`, the summary, the state reader, the four call readers and the journey rows come from one shared block of SQL text (`-- @call-rows`, with `-- @call-pointers` and `-- @call-identity`), copied byte for byte and checked by `reportsV3Contracts.test.ts`. Each reader runs it once, as a constant statement planned for the call's bounds (`EXECUTE ... USING`). The calls suite proves that the block's rows and carried columns equal the pinned v2 `report_call_facts`.
> - Journey facts read the organization's call history before `as_of` in one pass (`report_v3_journey_rows`). The pass is needed in full because unresolved activity and numberless calls count every unresolved call in the lookback, which requires every pointer to be resolved. Candidates (phase 1) are taken from that pass. Only the candidates' linked histories (every agent, every date) are then ordered. `report_v3_journey_facts_by` derives the scope's counts and every by_agent row's counts from that one member set. Each group counts only its own rows; nothing is summed or averaged.
> - Measured on the gate fixture (local PostgreSQL 16.15, 2026-11-02): the four call readers, scope and sales appointments are within 2 s. Summary and state at 366-day agency scope, and journey at every combination, are not within target. PostgreSQL 17.6 CI at the final head (5 samples) gives the same result; a faster runner missed only at 366-day agency scope. The gate result is reported in `WORK_LOG.md`, and the remedy named above (a separately approved maintained identity table) has not been requested or started.

**Gate** on the PG 17.6 harness at 500k calls, 5k sales and 10k appointments per org, under `SET LOCAL statement_timeout='8s'`:
- p95 ≤ 2s for scope, summary, state, sales_appointments and the four call readers;
- p95 ≤ 4s for journey;
- EXPLAIN (ANALYZE, BUFFERS) is recorded.

## 6. Default ACL, advisors, pin capture

- **Anon hazard:** the `public` default ACL grants anon, authenticated and service_role EXECUTE on every new function. Every class C file therefore revokes ALL from PUBLIC, anon, authenticated and service_role on each function it creates and grants nothing. Report grants come only from class E files. Application RPC grants come only from class W files, TO authenticated.
- **Evidence and ledger tables** (PKG-B–D): in `private`, RLS on, no policies, `REVOKE ALL` from client roles, no FK to `wins`. No rollback drops them.
- **Advisors** are compared by finding identity against the baseline (security ERROR 2 / WARN 213 / INFO 41; performance WARN 232 / INFO 230). Expected PKG-A delta: `authenticated_security_definer_function_executable` +9 (the nine v3 readers) and `unused_index` +2. Any new anon-executable SECURITY DEFINER finding, mutable search_path finding or ERROR stops the release.
- **Pin capture:**
  1. Apply the migrations in the disposable PG 17.6 harness.
  2. Read the md5(prosrc) tuples there (the stored text is authoritative).
  3. Write them into the enable.
  4. The release suite proves the enable passes and that every mutation refuses.
  5. The read-only preflight requires repo = harness = live for the closure.
  6. The read-back requires live v3 = pins.

  Two md5 methods are used, deliberately: preimage guards use `md5(pg_get_functiondef)` (e.g. `performance_sale_monthly` 51e06b46a13c3a8eec4d672bec158376); enable pins use `md5(prosrc)`.

## 14. Risks

- **8s timeout at heavy scopes**, now with four more call readers. Mitigations: two-phase journey facts, the concurrent campaign_lead index, window-bounded call facts, the p95 gate for all nine readers and a read-back that fails above 4s. Remedy: a separately approved maintained identity table, never a timeout increase.
- **Wrong ops script after v3.** `reports_integrity_enable.sql` seals v3 and `reports_disable.sql` leaves v3 on. Mitigations: A-38a and A-41, the named new scripts, runner stages that accept only pinned bytes, and a release test pinning (v2 off, v3 on).
- **Pin coupling with Leaderboard and Dashboard.** A change to `report_agency_time_zone` or `report_permission_flags` makes `reports_v3_enable` refuse until its pins are regenerated (fails closed; A-41).
- **Anon default ACL.** A missing REVOKE would expose a SECURITY DEFINER reader. Mitigations: class C postconditions, the class map and GRANT parser, the enable's effective-privilege check, S15 and the advisors gate.
- **Linked-identity effects E1–E6 at personal and team scope**, including through differencing filtered results. Mitigations: ★1 stays pending (the design is proposed; no reviewer has been appointed); the named security review of the actual SQL; S14a with the BC1 additions and S14b in both directions; options (c) and (b′) as a pinned constant.
- **Calls made differs from Leaderboard, Dashboard and old tabs** by non-attempts and unverified rows (12 for org A). Mitigations: one line in How it's calculated; ★9 offers a separately scoped alignment.
- **An accidental merge is a production release.** A PKG-F merge before C and D are live is a partial release. Mitigations: the BA-32 gate; a partial release only by explicit, labelled approval (★7).
- **"Deploy to production" ON** would auto-apply migrations on merge. Mitigation: the hard manual gate BA-23.
- **Invalid concurrent index.** Mitigations: lock_timeout 2s, the indisvalid check, refusal on an invalid leftover, and a retry only with a new approval.
- **PKG-B replaces `performance_sale_monthly`**, live for Leaderboard and Dashboard. The v3 window does not protect those consumers; D2's in-migration value-identity proof and the #486 coordination do.
- **Repository and production version drift** makes `db push` unsafe. Mitigations: renumber immediately before each backend merge; record history per file.
- **Harness drift from production columns.** Mitigation: `reports_v3_dependencies.sql` is checked against the live column inventory at preflight.
