# D6 — One-page Example 2 frontend (PKG-F)

## 1. Overview

PKG-F replaces the current Reports composition (`src/pages/Reports.tsx:136-160`) with one continuous Example 2 page of seven sections, in brief §18 order (§2.16). PKG-F creates **no database objects**. It consumes the PKG-A contract (§2.1–§2.5) and edits two CI files.

**Readers (§2.1).** The page requests only the nine v3 readers:
- `get_report_scope_v3(text)`: the page gate;
- `get_report_summary_v3(date, date, uuid, text)`: KPIs 1–11, 24, 25, 34;
- `get_report_journey_v3`: 14, 19, 21, 38;
- `get_report_sales_appointments_v3`: 12, 15–18;
- `get_report_state_breakdown_v3`: Regional performance (D5);
- `get_report_call_volume_v3`: calling heatmap, calling trend, call flow;
- `get_report_disposition_breakdown_v3`: call outcomes, call duration, disposition deep dive;
- `get_report_campaign_calls_v3` and `get_report_lead_source_calls_v3`: the call-only breakdowns.

The four call readers port the v2 call readers onto `private.report_v3_call_facts` and return call-only fields. Never requested (test-enforced): any of the six v2 readers, any v1 RPC, and `get_report_conversion_v3`, which does not exist. Old tabs (bundles built before PKG-F) keep calling the six v2 readers with their v2 meaning, and no v2 number is shown on this page.

**The browser computes no KPI.** Every value, numerator, denominator, coverage figure, maturity block, status and reason comes from a server envelope or a call-reader row. The only client arithmetic is for display:
- a row or cell rate from two exact server counts (heatmap cells, trend buckets, call flow, campaign and lead-source rows);
- weekly and monthly sums of the daily production and call series, in exact integers and cents;
- rounding exactly once (§2.5): the screen and the CSV each round from the exact numerator and denominator.

`src/lib/stat-computations.ts` (client ratios, :139-320) is deleted.

**One Calls made population (§2.10, R02).** Every call surface on the page counts confirmed attempts only (`attempt_class = 'attempt'`):
- KPI 5 = Σ heatmap.calls_made = Σ by_date = Σ by_hour = Σ disposition buckets = Σ campaign rows (including "Calls without a campaign" and "Other campaigns") = Σ lead-source call rows (including "Not linked to a current lead") = the state total;
- KPI 6 = Σ heatmap.contacted.

Refused admissions (3 live) are excluded as proven non-attempts and disclosed on demand. Rows with no admission record (9 live) are excluded and shown as missing evidence: KPI 5 is Partial with `attempt_unverified`, KPIs 8, 9 and 34 inherit the code, KPI 21 uses it for members with an unverified call before the first contact, and each call panel shows the compact Partial cue. Leaderboard, Dashboard and Trusted Dialer keep counting every outbound row; How it's calculated states the difference in one line.

**Release (§4).** PKG-F is last: PKG-A → PKG-B → divergence manifest → PKG-C and PKG-D (either order) → PKG-F. This release completes Reports V2 (§4.2). A protected preview is available from PKG-A onward, for Chris's review only. A public merge before C and D are live is only an explicitly approved partial release (★7). Every registry code already has a notice and a short cue, so no backend package needs a frontend redeploy.

## 3. Server design (consumed contract; no server objects)

Zod parses D1's shape verbatim. Nothing is renamed with `.transform()`.

**Meta** (`private.report_v3_envelope`, §2.1)
- `basis_version:'reports_v3'`
- `contract_version` matching `^3\.\d+\.\d+$` (≥ 3.3.0 when PKG-F releases)
- `reader` literal
- `scope`, `requested_scope`, `filter_agent_id`
- `window{time_zone, time_zone_source, start_date, end_date, start_at, end_at}` (verbatim `report_meta`)
- `as_of` = now() (there is no `p_as_of`)
- `agency_today`, `period_open`
- `basis{corrections, sale_call_links, appointment_evidence}` and `policy_basis{source, credit, date, premium}`
- `metrics:[envelope]`, in the exact order of `report_v3_kpi_ids(reader)`
- No top-level `time_zone` or `period`

**Envelope** (§2.2)

`{id, value, status, reason, numerator, denominator, coverage{eligible, assessable, unassessable, reasons}|null, maturity{window_days:30, state, members, pending, successes_to_date, mature_members, mature_successes, fully_mature_on}|null, detail}`

- `status` ∈ {available, partial, unavailable} describes the evidence behind `value`.
- `maturity` exists only on KPIs 12, 18 and 19 and describes pending 30-day outcomes. It is present whenever the cohort has members, **including when the value is unavailable** (§2.2 rule 7, BC4). `state = 'in_progress'` iff `pending > 0`. `value` is the observed result to date over the same assessable cohort, so a KPI can be Partial and In progress at once.

### 4.3 States, precision and notices

**Tiles (§2.16).** A tile carries its value and at most two text chips. Nothing is written under it.

| Envelope | Tile |
|---|---|
| available, no maturity or `state = 'complete'` | Value only |
| available, in progress | Observed value to date + "In progress" chip |
| partial | Value + "Partial" chip |
| partial, in progress | Observed value to date + "Partial" chip + "In progress" chip |
| unavailable | "—" + the reason's short cue (§2.3), or "Not enough data" when the reason is a coverage code; no status chip |
| unavailable cohort KPI (12, 18, 19) with a maturity block | As unavailable, plus the "In progress" chip while `pending > 0` (BC4) |
| loading / error | Skeleton / panel error with Retry |
| page | Denied, configuration, drift, v3-off "Reports unavailable" with Retry (R23) |

- An In progress tile always shows the observed value. It is never blanked.
- An unavailable cohort tile keeps its maturity details on demand (BC4): while `pending > 0`, its "In progress" chip opens the disclosure with the reason's notice, the pending count and "Fully mature on {date}"; once the cohort is complete, the same maturity lines are in Coverage in this report.
- Each chip is a button (`aria-expanded`) that opens a compact disclosure. It works by keyboard and closes with Escape. The disclosure lists:
  - the notice for `reason` and for every other code in `coverage.reasons`, with its count;
  - "Based on {a} of {e}" when coverage is present with `unassessable > 0` (once);
  - the exact numerator and denominator, observed to date;
  - while in progress: the pending count, "Fully mature on {date}" from `fully_mature_on`, and the mature-only counts (`mature_successes` of `mature_members`), labelled "Mature groups only" and never shown as a second rate under the metric's name.
- **Window-level conditions** (§2.2 rule 3, RL-2, RL-29) give the Partial chip without per-item unassessable counts. Each condition's count is in `coverage.reasons[<code>]`, with `coverage.unassessable` = 0 (RL-39):
  - `outcome_capture_partial_period`: the window straddles capture start; the disclosure reads "Outcomes recorded from {date}";
  - `capture_gap` for a disabled-capture interval, or a KPI 15 booking whose capture failed (counted, RL-42): "Some appointment changes were not recorded";
  - `history_incomplete` from numberless unresolved calls (§2.11): with `unassessable = 0`, the numberless-calls line (§4.4) replaces the "Based on {a} of {e}" notice;
  - `legacy_booking_basis` (KPI 15): legacy-classified bookings are counted, so a legacy-only window (Aug–Sep 2026) shows its value with the Partial chip, never "—"; the disclosure reads "Includes {n} bookings classified from older records".
- The same lines appear in How it's calculated → Coverage in this report (§4.4). One formatter in `reports-kpi-format.ts` builds them for both.
- **Premium notices (KPIs 1 and 4) follow the RL-11 precedence**, which is the registry order (`premium_invalid` before `premium_missing`):
  - no usable premium: "—" with "Not enough data" when any premium is invalid (`premium_invalid`), otherwise "—" with "Premium not entered";
  - some usable premiums: the Partial chip, whose disclosure leads with "{n} premiums need review" when any premium is invalid, otherwise "{n} policies missing premium"; the other code's line follows when it also applies;
  - no policies: KPI 1 shows $0.00 (available) and KPI 4 shows "—" with "No policies".
- An unavailable tile's short cue is plain text. Its notice is in Coverage in this report and in the tile's screen-reader text.
- Status is never conveyed by colour alone: every state has its text chip or cue.
- Values never erase evidence states (§2.2 rules 5–6, BC4). A complete 0 over a positive denominator is a valid 0 (or "0.0%") and keeps the chip its status implies. Missing numerator evidence is never shown as 0: an unavailable KPI shows "—" with its cue. For example, KPI 15 with `evidence_not_captured` shows "—" and "Not tracked yet", and KPI 5 with 0 confirmed calls and 3 unverified shows "—" and "Not enough data".

**`kpiEnvelopeSchema.superRefine`.** D1 owns the schema. It mirrors `report_v3_metric` (§2.2), and a violation fails only that panel, closed:
- **unavailable** (generalised rule 2, BC4): `value` null; `reason` is a config code, a zero code, or a coverage code. A coverage code requires `coverage.assessable = 0`, or a known `denominator` of 0 with `coverage.unassessable > 0`.
- **partial:** `value` non-null; `reason` is a coverage code; coverage non-null with `unassessable > 0`, or one of the four window-level conditions applies (`outcome_capture_partial_period`, `capture_gap` for a disabled-capture interval or a KPI 15 gap booking, `history_incomplete` from numberless unresolved calls, `legacy_booking_basis`; RL-2, RL-29).
- **available:** `value` non-null, `reason` null, coverage null or `unassessable = 0`.
- **A known denominator of 0** ⇒ unavailable, never a ratio: the KPI's zero code when nothing on that side is unassessable, otherwise a coverage code with `coverage.unassessable > 0`.
- **maturity:** only on 12, 18 and 19, and present whenever the cohort has members (`maturity.members > 0`), whatever the status, including unavailable (BC4). An available or partial 12, 18 or 19 envelope always carries it. `window_days = 30`; `state = 'in_progress'` iff `pending > 0`. Status and maturity are independent, so partial + in progress and unavailable + in progress are valid.
- assessable + unassessable = eligible, and every key of `coverage.reasons` is a coverage code.
- The reason is one of the 29 registry codes and is never `panel_not_loaded`. Any other code, including the three removed in revision 2, fails Zod.

**Precision (§2.5).** `roundHalfUp(n, d, k) = floor((2·n·10^k + d) / (2·d)) / 10^k` in integer arithmetic, using BigInt when a product exceeds 2^53. It returns a string with exactly k decimals.
- Percentages multiply n by 100 first.
- Medians and currency are rounded once from the exact value: a median's value (at most 6 dp) is scaled to an exact integer of millionths before rounding, and currency is exact cents.
- The screen (§2.4 display precision; currency by `formatPremium`) and the CSV (§2.4 CSV precision: 2 dp for ratios and currency, 1 dp for percentages and medians) each round from the exact numbers. Display is never computed from the CSV value, and neither is computed from a pre-rounded server value.
- Examples: (1249, 1000) → display 1.2, CSV 1.25; (9, 4) → 2.3; (115, 100) → 1.2; (0, 5) → 0.0; 1/3 as a percentage → 33.3.
