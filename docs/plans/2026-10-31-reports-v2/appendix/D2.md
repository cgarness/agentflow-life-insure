### 3.2 PKG-A helpers (`…11_reports_v3_sale_facts.sql`)

```sql
-- PKG-B stub (main plan §2.6). The value comes ONLY from the shared choke point; source/state are classified from wins columns.
CREATE FUNCTION private.report_v3_sale_premium(p_win public.wins, p_client numeric)
RETURNS TABLE(monthly numeric, premium_source text, premium_state text, revision integer) LANGUAGE sql STABLE AS $$
 SELECT m.v,
  CASE WHEN p_win.premium_snapshot THEN 'sale_snapshot'
       WHEN nullif(p_win.premium_amount,0) IS NOT NULL THEN 'legacy_sale_event'
       WHEN f.fb IS NOT NULL THEN 'legacy_record_fallback' ELSE 'none' END,
  CASE WHEN m.v IS NOT NULL THEN 'known'
       WHEN (CASE WHEN p_win.premium_snapshot THEN p_win.premium_amount
                  ELSE coalesce(nullif(p_win.premium_amount,0), f.fb) END) < 0 THEN 'invalid'
       ELSE 'missing' END, 0
 FROM (SELECT private.performance_sale_monthly(p_win,p_client) v) m
 CROSS JOIN LATERAL (SELECT CASE WHEN p_win.idempotency_key ~ ':policy:[0-9]+$' OR EXISTS(SELECT 1
   FROM private.policy_identities i WHERE i.organization_id=p_win.organization_id AND i.policy_id=p_win.policy_id
   AND i.source='additional') THEN NULL ELSE nullif(p_client,0) END fb) f $$;

CREATE FUNCTION private.report_v3_sale_facts(p_org uuid, p_agents uuid[], p_sold_from date, p_sold_until date)
RETURNS TABLE(win_id uuid, policy_id uuid, buyer_id uuid, seller_id uuid, sold_date date, created_at timestamptz,
  recorded_at timestamptz, event_time_source text, monthly_premium numeric, premium_source text, premium_state text,
  correction_revision integer)
LANGUAGE sql STABLE AS $$
 SELECT w.id, w.policy_id, w.contact_id, w.agent_id, w.sold_date,
        w.created_at, coalesce(w.recorded_at, w.created_at), w.event_time_source,
        e.monthly, e.premium_source, e.premium_state, e.revision
 FROM public.wins w
 LEFT JOIN public.clients c ON c.id=w.contact_id AND c.organization_id=w.organization_id
 CROSS JOIN LATERAL private.report_v3_sale_premium(w, c.premium) e
 WHERE w.organization_id=p_org AND w.policy_id IS NOT NULL AND w.sold_date IS NOT NULL
   AND (p_sold_from IS NULL OR w.sold_date >= p_sold_from)
   AND (p_sold_until IS NULL OR w.sold_date < p_sold_until)
   AND (p_agents IS NULL OR w.agent_id = ANY(p_agents)) $$;
```

> **Batch 6 clarification (2026-11-02).** In `…11` the stub is `LANGUAGE plpgsql STABLE` with the same signature, the same delegation to `performance_sale_monthly` and the same classification of source and state. A nested SQL function call is set up again for every sale, so the SQL form cost about 200 µs per sale; the PL/pgSQL form costs about 72 µs. The code above states the rules.

- **Value.** The stub never decides a value, so v3 cannot disagree with the Leaderboard. A test asserts `monthly IS NOT DISTINCT FROM performance_sale_monthly(w, c.premium)` for every fixture win.
- **Columns.** Exactly the main plan §2.6 list, in that order. `buyer_id` is `wins.contact_id` and `seller_id` is `wins.agent_id`. `correction_revision` is 0 until PKG-B, then the head ledger revision.
- **Indexes and joins.** Bounded calls use `performance_wins_org_sold_date` (`20261017043757`). Every win with a `policy_id` has a same-org policy identity (`wins_policy_registry_fk`), and `wins_policy_identity` keeps one sale per policy, so a policy is never counted twice.
- **Timestamps.** `recorded_at` falls back to `created_at` for the 6 legacy NULLs. The helper applies no as_of filter; callers filter `recorded_at <= as_of`.
- **`premium_state`:**
  - **known:** a non-null value. A snapshot 0 is a known $0 (#40/:618). `policy_sale_values` stores a blank premium as 0 (`20261004000819:42`); live there are 0 zero-premium sales.
  - **invalid:** the would-be amount is negative. The writer rejects negatives (`:39`), so only legacy rows can be invalid. Live: 0.
  - **missing:** everything else, including a snapshot NULL, a legacy sale with no fallback, and a correction to unknown.

**`private.report_v3_production(p_org uuid, p_agents uuid[], p_sold_from date, p_sold_until date, p_as_of timestamptz) RETURNS jsonb`.** LANGUAGE sql, STABLE. It raises 22023 if either bound is NULL. The summary reader passes `report_v3_sold_window(start_date, end_date, agency_today)` and its `as_of` (`now()`), so a future-dated sale counts once its date arrives.
```
{ totals: {policy_count, buyer_count, known_count, missing_count, invalid_count, monthly_premium, annual_premium,
           premium_sources:{sale_snapshot, legacy_sale_event, legacy_record_fallback, correction, none},
           corrections_applied, client_record_deleted, unattributed_annual_premium|null, stored_without_sale|null,
           quality:{undated_policies, missing_policy_identity|null, unattributed_policies|null}},
  by_agent: [{agent_id, policy_count, buyer_count, known_count, missing_count, invalid_count, annual_premium}],
  production_by_date: [{date, policies_sold, annual_premium, premium_known, premium_missing, premium_invalid}] }
```
- **Input.** One materialized pass over `report_v3_sale_facts(…) WHERE recorded_at <= p_as_of`.
- **Amounts (main plan §2.5).** `annual_premium` = Σ monthly × 12 over known rows. Every sum is exact numeric and is never rounded by the server. Every monthly amount has at most 2 decimals (the sale writer and the ledger CHECK enforce it, and the preflight asserts 0 legacy exceptions), so every AP is exact cents. by_agent and by_date rows sum exactly to the totals.
- **Buyers.** `buyer_count` = distinct `buyer_id`, deduplicated again at scope. It is never the sum of the rows. `client_record_deleted` counts sales whose `buyer_id` has no `public.clients` row in the organization; they still count as buyers.
- **by_agent.** One row per credited seller. D1 merges these into the roster rows `{agent_id, name, status, credit, metrics}`. `credit` maps every KPI id in the row to its basis, here `{"1": "original_seller", "2": "original_seller", "3": "original_seller", "4": "original_seller"}` (main plan §2.4). A roster agent with no sales gets available 0 for KPIs 1–3 and unavailable `no_policies_sold` for KPI 4.
- **Unattributed sales** (`agent_id IS NULL`) are included only when `p_agents IS NULL`. They count in the totals, are reported in quality, and get no by_agent row. Live: 0.
- **production_by_date** is daily and zero-filled over [p_sold_from, p_sold_until). Dates after agency today are not emitted. D6 sums the rows for weeks and months.
- **Disclosures:**
  - `quality.undated_policies`: the in-scope credited sales with `policy_id` set and `sold_date` NULL, all time.
  - `quality.missing_policy_identity`: wins with `policy_id` NULL.
  - `stored_without_sale`: `private.report_v3_stored_without_sale(p_org) RETURNS bigint`, which counts policy identities with no sale event and credits no one.
  - `missing_policy_identity`, `stored_without_sale`, `unattributed_policies` and `unattributed_annual_premium` are agency scope only and null otherwise, so nothing org-level leaks (main plan §2.9). Live: all 0.

**`private.report_v3_production_kpis(p_counts jsonb) RETURNS jsonb`** is IMMUTABLE. It returns the id 1–4 envelopes for the totals and for each by_agent row, built only by the foundation builders (`report_v3_total` for KPIs 1–3, `report_v3_ratio` for KPI 4), so status and reason come from `report_v3_evaluate`, `private.report_v3_metric` validates the result, the main plan §2.2 rules hold and a violation raises P0001. `maturity` is always null: KPIs 1–4 are not 30-day group KPIs. Notation: P = policies, K = known, M = missing, I = invalid (P = K + M + I), A = known AP.

**Reason order (main plan §2.2 rule 8 and status truth table; RL-11, RL-14).** `reason` is the first applicable code in registry order. For KPIs 1 and 4 the candidates, in that order, are:
1. `no_policies_sold` (#6, zero; KPI 4 only): P = 0;
2. `premium_not_entered` (#14, zero): P > 0, no usable premium and none invalid (K = 0, I = 0);
3. `premium_invalid` (#27, coverage): I > 0;
4. `premium_missing` (#28, coverage): M > 0.

`coverage.reasons` carries `premium_invalid: I` and `premium_missing: M`, each when it is > 0.

| KPI | Value, numerator, denominator, coverage | Status and reason |

- **Detail (main plan §2.4, X6):**

`private.guard_policy_sale_premium_correction()`:
- **BEFORE INSERT:**
  - requires `current_user = 'postgres'`, else 42501;
  - requires a win with this `id` and the same organization, `policy_id`, `contact_id = buyer_id`, `agent_id` and `sold_date` (the same-org guard);
  - requires revision = head + 1, `supersedes_id` = the head's id, and `previous_effective_monthly` = the head's `corrected_monthly`;

- **BEFORE UPDATE OR DELETE (row) and BEFORE TRUNCATE:** raise 23514 "Sale premium corrections are append-only".

**Reversal.** A ticketed reversal of a corrected win still succeeds. Its ledger rows stay, and they become inert because every reader starts from `wins`.

### 3.4 Effective reader and performance switch (in `…20`)
```sql
CREATE FUNCTION private.policy_sale_effective_premium(p_win public.wins, p_client numeric)
RETURNS TABLE(monthly numeric, source text, state text, revision integer) LANGUAGE sql STABLE AS $$
 -- head correction (latest revision) if any: (corrected_monthly, 'correction', known|missing, revision);
 -- else the verbatim original rule: performance_monthly(snapshot, amount, fallback-or-NULL) with the
 -- identical source/state classification as report_v3_sale_premium, revision 0. Never calls performance_sale_monthly.
$$;
```
Migration `…20` runs `SET LOCAL lock_timeout='2s'; SET LOCAL statement_timeout='15s'` and then:
1. **Guards.**
   - v3 is disabled: no `get_report_%_v3` is executable by authenticated. `performance_sale_monthly` is pinned only in `reports_v3_enable.sql`, so it changes only in the v3-only window (A-41).
   - Preimage: `md5(pg_get_functiondef('private.performance_sale_monthly(public.wins,numeric)'::regprocedure)) = '51e06b46a13c3a8eec4d672bec158376'`.
   - Its metadata (owner, prosecdef, volatility, proconfig, ACL) is saved to a temp table.
   - The new objects are absent, so a replay refuses.
2. Snapshot `(win_id, performance_sale_monthly(w, c.premium))` for every win into an `ON COMMIT DROP` table.
3. Create the ledger, the guard, `private.policy_sale_book_monthly(p_raw jsonb, p_primary boolean)` and the effective reader.
   - `policy_sale_book_monthly` reads a JSON number exactly. It parses a string with the `report_monthly_amount` grammar (`20261006043738:51-61`). A primary 0 becomes NULL (#34).
   - It is not report-prefixed, so a v3 structural rollback can never break the writer.
4. `CREATE OR REPLACE private.performance_sale_monthly` with the body `SELECT e.monthly FROM private.policy_sale_effective_premium(p_win,p_client) e`. The signature and every saved attribute stay the same.
5. Re-evaluate every win. Any difference, or any metadata change, raises. The ledger is empty at this point, so no number changes.
6. Create `correct_policy_sale_premium` and `get_client_policy_sale_premiums` **sealed** (REVOKE ALL from PUBLIC, anon, authenticated, service_role). `…20` is class C and has no GRANT; `…21` grants them.

```sql
public.correct_policy_sale_premium(p_request_id uuid, p_policy_id uuid, p_expected_revision integer,
  p_expected_effective_monthly numeric, p_expected_book_amount jsonb, p_corrected_monthly numeric,
  p_reason_code text, p_note text, p_book_mode text) RETURNS jsonb
LANGUAGE plpgsql VOLATILE SECURITY DEFINER SET search_path = pg_catalog, pg_temp SET lock_timeout = '2s';
```
There is no function-level statement_timeout. The authenticated 8s limit applies, and the RPC is budgeted under 8s by test.

Body:
1. **Authorize.** `private.campaign_actor()`. Under the proposed default (★5, §6.3) the actor must have `actor_role IN ('Admin','Super Admin') OR is_super` in the home organization, else 42501.
2. **Validate.** Otherwise 22023, with DETAIL `invalid_request | invalid_amount | invalid_reason | invalid_note | invalid_book_mode | invalid_revision`. An amount must be ≥ 0, have at most 2 decimals and be ≤ 1,000,000.
3. **Hash and replay.**
   - `payload_hash` = sha256 hex of `jsonb_build_array(policy, expected revision, expected effective, expected book, corrected, reason, btrim(note), mode)`.
   - Take an advisory xact lock on `org:sale-premium-correction:request:<id>`.
   - An existing row with the same actor and hash returns `result || {idempotent:true}`. Otherwise PT409 `request_conflict`.
4. **Locate and lock.** Find the sale in the actor's org, else PT404 `sale_not_found`. Take the per-policy advisory lock, then the client row `FOR UPDATE`, the same row lock as `update_client_with_policy_sale`.
5. **Stale checks.**
   - Head revision ≠ expected, or effective ≠ expected → PT409 `stale_revision`.
   - Raw book value ≠ expected → PT409 `policy_changed`.
   - Corrected = current → 22023 `no_change`, with one exception, the **freeze** (RL-15): when the current effective source is `legacy_record_fallback`, a same-amount revision is accepted. It records `previous_source = 'legacy_record_fallback'`, and from then on the sale no longer follows the book.
6. **Book.** The book is the primary (`to_jsonb(c.premium)`), or exactly one additional element matching `policyId` (`elem->'premiumAmount'`), or none.
   - `keep_current` → `kept_current`, or `no_policy_record` when there is no book entry.
   - `match_sale` with no book entry → 22023 `no_policy_record`.
   - `match_sale` where the parsed book = corrected → `already_matched`.
   - `match_sale` where the parsed book = the effective amount before the correction:
     - a primary to 0 → 22023 `book_zero_unsupported`;
     - otherwise update `clients.premium`, or `jsonb_set(…,'{additional_policies,idx,premiumAmount}', coalesce(to_jsonb(p_corrected_monthly),'null'))`, plus `updated_at` → `updated`.
   - Any other `match_sale` → 22023 `book_diverged`.
   - The existing client triggers fire. The test asserts 0 wins inserted.
7. **Insert** the ledger row (revision = expected + 1).
8. **Return** `{policy_id, win_id, request_id, revision, previous_effective_monthly, corrected_monthly, effective_annual, book_action, freeze, sold_date, seller_id, corrected_at, idempotent:false}`. The B6 manifest records `request_id` (§6.7).

The RPC never writes `wins`, `policy_identities`, `policy_sale_receipts` or any `policy_commission_*` table, and never calls `notify_win`. The Leaderboard realtime listener watches only wins INSERT (`useLeaderboardData.ts:854-855`), so open boards show a correction on their existing poll (§6.4).

### 3.6 History RPC
`public.get_client_policy_sale_premiums(p_client_id uuid) RETURNS jsonb`. STABLE SECURITY DEFINER, with the same search_path and no timeout setting. It makes one call per contact view.
- **Visible policies:** the actor's org sales where `contact_id = p_client_id`, and the viewer is Admin/SA, is `w.agent_id`, or is a Team Leader with `public.is_ancestor_of(uid, w.agent_id)`.

- `book`, `can_correct` and each history `request_id` are filled for Admin/SA only (null otherwise). An invisible or cross-org client returns `policies: []`.

## 6. AP correction lifecycle, pre-cutover reconciliation and the divergence manifest

### 6.1 Correction versus later policy change
| | Correction | Later policy change |
|---|---|---|
| What it is | Fixes an entry error in the original sale | A genuine change to the policy after the sale |
| Path | Only **Correct sale premium** in the policy section → `public.correct_policy_sale_premium` | The existing Edit Client premium and additional-policy edits (`supabase-clients.ts:152` → `update_client_with_policy_sale`), unchanged |
| Writes | One ledger revision; with `match_sale`, also the current policy record (D2-5) | The current policy record only; never the ledger |
| Sale AP | Restated on the original seller and the original Sold Date, everywhere performance and Reports V2 read (§4.2) | Never moves (one legacy exception, below) |
| v2 book readers, commission basis | Move only when `match_sale` updated the book; saved commission rows never change (A-851) | Move as today |

- The edit forms get no new prompt, field or link. Edit paths never call the correction RPC and never write the ledger.
- **Legacy exception (A-40, RL-15).** The 1 legacy-fallback sale (`premium_snapshot = false`, no event amount) takes its sale premium from the current primary premium, so a book edit still moves its AP until an Admin records a correction or a same-amount **freeze** (§3.5). ### 6.7 Divergence manifest and its check (manifest step B6)
- **When.** Main plan §9.2 B6: after the PKG-B backend stages (B1–B4) and the correction UI merge (B5); before PKG-C, PKG-D and PKG-F (§4.1 step 3). Chris approves the classification one dimension at a time (main plan §4.3).

  - a Sold Date classification ∈ {`entry_error`, `genuine_later_change`}, reviewed on its own evidence and never inferred from the premium decision;
  - `decided_by` and `decided_at` for each classification;
  - for each premium `entry_error`, the ledger `request_id` of its correction (from the Admin history list, §3.6).
- **Premium.** An `entry_error` is corrected only through **Correct sale premium** (usually `match_sale` → `already_matched`, because the book already holds the corrected amount). A `genuine_later_change` gets no correction; the reviewed manifest row is its record.
- **Sold Date.** No correction path exists (D2-9), so the sale keeps its original Sold Date. No database count is invented for `genuine_later_change`, whose record is the reviewed manifest.
- **Never** an automatic rewrite, direct SQL or a batch.
- **Completion gate** (main plan §4.2 item 3): the manifest is approved, the check passes, and every Sold Date `entry_error` is either corrected by a separate package or explicitly accepted by Chris.

## 12. Risks
- Replacing `performance_sale_monthly` restates every performance surface at once. It is value-identical at release, but pin 51e06b46… changes, so branches that pin it (PR #486) must rebase.
- A later policy change (Edit Client or an additional-policy edit) never moves sale AP; an entry error in the original sale needs **Correct sale premium**, which only Admins can use under the proposed default (★5). The "Sale premium $X/mo (as sold)" line makes the difference visible.
- The 1 legacy-fallback sale is the exception: under A-40 its sale premium is the current primary premium, so book edits move its AP until an Admin corrects or freezes it (RL-15). How it's calculated discloses it meanwhile.
- Commission estimates keep their basis (D2-8, A-851). A corrected AP can sit next to an older commission basis.
- Open views show a correction only on their next refresh (§6.4): the Leaderboard poll, a Dashboard load or Refresh, a Reports load, filter change or Refresh. There is no new polling or realtime. Old v2 Reports tabs never show corrections; they read the book.
- Agency Group peers can still read raw `wins.premium_amount` through `wins_select` (original values), while boards show the effective amount.
- A blank premium saved as a snapshot 0 counts as a known $0 (#40). Live: 0 such sales.
- A legacy amount with more than 2 decimals would make AP a non-whole number of cents. Values stay exact and are rounded once at display or export; the preflight asserts 0 such sales.
- Admin-only correction may be too narrow (★5). Sold Date entry errors have no correction path until D2-9's package; one found at B6 blocks completion unless Chris accepts the disclosed difference.
- PR #486's record-later backfill must follow the B6 classification. Its migration 20261023180000 sorts below the head.
- The composed fixture can drift from production.
- The Reports V2 browser check runs only in PKG-F, when the page exists. The other AP surfaces are covered from PKG-B by the SQL harness and `correctedPremiumSurfaces.test.tsx`, whose payload cases run only where `REPORTS_SQL_PAYLOADS` is set (the reports-backend.yml step).
