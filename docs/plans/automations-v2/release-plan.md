## Backing out a stopped installation

Run `rollback/20261124100600_automation_v2_stopped_install.rollback.sql` as one transaction, outside calling hours:

```bash
psql -X -1 -v ON_ERROR_STOP=1 -f supabase/migrations/rollback/20261124100600_automation_v2_stopped_install.rollback.sql
```

It refuses outside a transaction; when the installed files are not exactly the first k of the seven, or none or all seven are in; while any agency has enrollment, message delivery or the builder on; when V2 has recorded anything (a pinned SMS purpose, an event only V2 records, a task receipt, a callback, a recorded late-answer cleanup or an issuance confirmation) or any published version uses something only V2 runs; when a function it replaces differs from what the installed files give it; and when it already ran. It restores the first-release body of every function the installed files replaced, byte for byte, turns the observers they added into no-ops whose triggers stay attached, changes no row, and records itself in `private.automation_v2_backed_out()`. The probe then reports `backed_out` with no next file, and every V2 file refuses to install, because the files after the ones backed out would run beside restored first-release functions. Take the V2 files that were not applied out of the branch's `supabase/migrations/` afterwards, so a later ordered migration run does not stop on their guard. Installing V2 later is a new migration.

## Rollback order after a complete installation: fence first, then frontend

1. **Fence.** Set `enrollment_enabled=false` and `dispatch_enabled=false` for every agency and read both back. From this moment no automation creates a task or callback, and no message is handed to a provider. Runs already under way hold until the fence is lifted; while the V2 functions are installed, a run on hold for seven days ends.
2. **Hand over open callbacks.** The previous frontend has no callback list. Before restoring it, list each agency's open and claimed callbacks and give them to the agency for manual follow-up:

   ```sql
   select b.organization_id, b.status, b.caller_phone, b.claimed_by, b.created_at, b.title
   from public.inbound_callbacks b where b.status in ('open','claimed')
     and private.automation_inbound_evidence(b.organization_id, b.call_id) is distinct from 'answered'
   order by b.organization_id, b.created_at;
   ```

   A callback whose call was proven answered but whose cleanup is still waiting is left out, as the callback list already leaves it out.

   Tasks automations created stay on the contacts, with their time of day.
3. **Frontend.** Promote the deployment recorded at preflight as the rollback target. A draft that uses V2 content opens for inspection only in the first-release editor. A first-release draft stays editable.
4. **Worker.** There is no earlier Automations worker to restore. If the V2 worker was released, keep it, or turn its schedule off. Against the restored functions it runs first-release versions exactly as the first release defines them. After step 5, while the fence is still on, turn the schedule off: the restored first-release functions retry a held step every five minutes with no end.
5. **Database, only if the V2 functions themselves are at fault.** Run [`rollback/20261124100600_automation_v2.rollback.sql`](../../../supabase/migrations/rollback/20261124100600_automation_v2.rollback.sql) as one transaction, outside calling hours:

   ```bash
   psql -X -1 -v ON_ERROR_STOP=1 -f supabase/migrations/rollback/20261124100600_automation_v2.rollback.sql
   ```

## The complete current production schema

Chris asked for the seven migrations and both rollbacks to be rehearsed on an isolated copy of the complete current schema, with that copy verified against an independent reading of production.

- **What changed in this round.** `release-full` used to apply the files to a filtered `pg_dump` copy that nobody fingerprinted (no cron schema, no GraphQL wrapper privileges, no database privileges or settings). It compared the restored database only with the bundle's own reading, and took its receipts from this checkout by default (the November 21 reading, now stale). Now:
  - the receipts are a separate directory read through the Management API within two hours of the dump. Each reading names its connection (its application name and session user). Three kinds of receipt are refused: one that names any connection other than the Management API's own (`mgmt-api`), such as the bundle's (`agentflow-schema-bundle`) or a default `psql` login; a schema or canonical receipt taken at the same moment as the bundle's matching reading; and a copy of a bundle file, byte for byte or reformatted. The name is what the reading reports, so this catches a wrong or copied receipt, not one deliberately labelled `mgmt-api` (see the handoff's "What it does not prove");

## Decisions for Chris

- **Wider rollout.** Issuance confirmation, the Inbounds callback list and the phone contact-screen pan are scoped to the pilot. Opening any of them to other agencies, before or after this release, is a separate decision.
- **Complete-schema rehearsal.** Whether to produce the archive bundle and run `run.sh release-full` before approving the migrations, or to accept the dependency comparison above as was done for the first release.
- **Stop rules across a reschedule.** When a reply, a conversation or another booking has ended an automation's reminders and the appointment is then moved while it stood, the automation starts again for the new time, counted from the move. This round keeps that, because it predates the round and the builder describes stop rules per run. A booking taken up after its appointment was reopened is judged as the run that followed the appointment would have been: from the latest booking the automation followed while the appointment stood, an ordinary move counting from itself. A move back to the time a run's reminders were for is judged the same way: an ordinary move back counts from itself, while a move back made while the appointment was cancelled counts from the latest booking the automation followed while it stood, so a reply or conversation since then still ends the reminders. Whether stop rules should also outlive an ordinary reschedule is a product decision; the tests pin today's behavior.
- **A person's stop lasts for its own run** (decided this round, to confirm). Reopened at the time the stopped run followed, nothing starts, whether on the same slot or on another slot at that time (moved away and back while cancelled); at a new time, by a reschedule or a reopening, the reminders start over, as after a reply. The times a stopped run followed are the slot of its appointment wait, else of its reminders, else of its booking (for a run that never reached an appointment wait, also the time the appointment last stood at before the run ended), the time the appointment stood at when it was stopped, whatever slot its wait still named, and each time it stood at when the run handed a message to a provider (dated by its handoff, or by its first lease when there is no message record, as with synthetic transports) or created a task, all by the change log. A slot the appointment was moved to while cancelled is not one of them until a save opens it there, so a stop made while the appointment was still cancelled does not hold the new time, also when the worker had not yet processed the cancellation; a stop made after the reopening holds it, also when the worker had not yet processed the reopening, so that new time gets no reminders (scenarios N1 405 and M8 619). A run that completed holds, on a reopening, the time it ended at, also after a run for another time came in between, and also when the sync's one save moves the appointment back and writes Scheduled; it does not hold a time it passed through and then left (a known limitation below). A run that failed holds the same only once it gave something other than the message that failed (a text whose provider outcome is unknown counts, lead 307), so a time whose first message the provider rejected still gets its reminders when the appointment comes back to it on another slot (lead 289); reopened on the same slot, nothing starts again. A message the provider accepted and then reported failed or undelivered counts as the message that failed (see the decision below). The stop after seven days on hold holds like a person's stop while its run is the automation's latest booking run for the appointment (every later booking run counts, also one a move back later replaced; lead 286) or once it gave something; one that gave nothing holds no time once a later run followed another time, so that time gets the reminder the hold kept from going out. The cancellation carry-on and the move back read the same rule (`private.automation_time_held`). The carry-on carries no run that never followed a time on to it while another booking run holds it: a run whose reminders were for a slot is recorded as rescheduled, and a later move back to that slot's time carries it on; one whose reminders were for no slot stays stopped by the cancellation, and a later reopening or move to a time it followed, or to one no other booking run of the automation holds, carries it on from its step, so a new time gets only the steps it has left (leads 274 to 277, 304 and 305). The move back carries no run on to a time another booking run holds, and at most one run of the automation carries on (leads 278 to 285). The appointment suite pins these cases (leads 254 to 296, 300, 304, 305 and 307). Keeping a person's stop for the whole appointment would also change ordinary reschedules.
- **A booking's message while its appointment is marked No Show or Completed** (decided this round, to confirm). While the appointment is still ahead, the final send check (`private.automation_message_issue`) holds a booking's message when the current slot holds an outcome other than a retraction, as admission refuses such a slot: an outcome taken back before the start lets the message out once. Otherwise the message stays held until the start, when the started rule skips a reminder timed before it. The seven-day hold ends the run only when the message is held that long before the start; an outcome taken back after that, still before the start, by a save the worker is told about (a person's save that records the take-back on that slot, or a change to Cancelled and a reopening), lets the cancellation carry-on carry the run on at a time it followed (for a run that had not reached an appointment wait, also the time the appointment stood at when the hold ended it, unless another booking run of the automation holds that time; an earlier run that passed through that time and left, or that a stop rule ended, does not hold it, so what it gave there is given again, as without the outcome: scenarios M2 935, M4 949 and W1 961), unless, for an automation that stops on a reply, a verified reply came after its stop basis, so the held message still goes out and the time keeps its later reminders (leads 287, 288, 297 to 299, 301 to 303 and 308). A run that has passed no appointment wait then follows a later ordinary move in place, so the new time gets only the steps the run has left (scenario S10 939). When the run had not reached an appointment wait and the hold also ended an earlier booking run of the automation after it gave part of that time's sequence, the earlier run holds the time and only the latest run is ever carried on, so neither goes on and the time keeps only what the earlier run gave (scenario S16 961). A take-back made only after the start carries nothing on, so a follow-up timed after the start is not sent either (scenario Z5 650). A person's outcome stands over a later save by the calendar sync, as admission reads it, so the message stays held while the calendar shows Scheduled, until a person takes the outcome back by setting another status first or by moving the appointment, since saving Scheduled over the sync's Scheduled records no take-back (scenarios M10 653 and Z4 610). Once the appointment has started an outcome is expected, so the started rule decides: a reminder timed before the appointment is skipped, and a follow-up timed after it goes out, whatever outcome the slot holds (lead 296). A move or a cancellation after the worker picked up the reminder still refuses it. The appointment suite pins the hold, the take-back and the seven-day limit (leads 251 to 253), the take-back after that limit (leads 287, 288, 297 to 299, 301 to 303 and 308), the reason text that take-back depends on (lead 306; a run whose last held lease gave another reason, such as an eligibility check that could not run, is not taken up) and the started rule after the start (lead 296).
- **A message the provider accepted and then reported failed or undelivered** (decided this round, to confirm). Such a message fails its run, and a run that failed holds its time only once it gave something other than the message that failed. So when the appointment comes back to that time on another slot (moved away and back while cancelled, then reopened), the automation sends that message again. The provider reported that the customer did not get it, so this is a retry, not a second message (scenarios X8 675 and X12). Counting a message the provider accepted as given (one with a provider message id) would send nothing again there; that option was tried on the scenarios but is not ready.
- **A calendar sync's save after a cancellation** (decided this round, to confirm). The inherited two-way sync writes Scheduled over every changed Google event that Google does not show as cancelled. The CRM's own update after a person cancels in the CRM changes the Google event without cancelling it, so the next inbound sync rewrites the appointment as Scheduled. So a save without a signed-in person takes back only a cancellation such a save recorded on the current slot, and a person's cancellation, No Show or Completed on that slot stands over it. A person's retype changes neither: it restates the record it supersedes, found through the slot's outcome chain. The reminders stay stopped, so a customer who cancelled is not messaged. Two cases follow. First, a move made while the appointment is cancelled opens a slot with no outcome, so the appointment's own status decides there, and a sync's Scheduled on that slot resumes the reminders. So does the sync's one save that moves the appointment and writes Scheduled after a person cancelled, because that save opens such a slot itself. The change log records who saved (`actor_id`, empty for the sync), so these could wait for a person's save instead. That is your choice; this round leaves them as they are. Second, once the sync has rewritten Scheduled over a person's cancellation, the calendar shows Scheduled but the reminders stay stopped. A person's save that keeps an open status (Scheduled or Confirmed), or a retype, does not resume them. A status round trip (No Show, Cancelled or an ignored status, then Scheduled) or a move does, by a person or by the sync: a move of the Google event, or Google cancelling and restoring it, resumes them too. Fixing the inherited overwrite, so that a cancellation made in the CRM cancels the Google event or survives the inbound sync, would remove both cases. The appointment suite pins these cases (leads 185 to 187, 205 to 210, 215 to 218, 246 and 247).
- **An appointment entered as cancelled is judged from that entry** (decided this round, to confirm). A reply or a conversation while it was on file as cancelled ends its reminders once it is opened, whenever the reply is verified. Judging it from when it was opened instead would need V2 to replace an eighteenth first-release function, the reply cancellation (`private.automation_cancel_reply`).
- **A reply verified late across a move back** (known limitation, kept this round). When a reply was received after the run's booking and before a move back (between the moves, or before the move away), but verified only after the worker processed the move back (an email synced late, or a reply repair), the first release's reply cancellation ends the run the move back carried on, because it compares the run's own booking time. That run's later reminders are then lost; nothing is sent twice. Replacing the reply cancellation, as above, would fix it.
- **A message for a reopened booking counts from the reopening** (decided this round, to confirm). The rule that skips any message for an appointment that now begins at or before its booking treats a reopened booking's reopening as its booking, as admission and pacing do. An appointment moved to a time between the booking and the reopening is then skipped even for a message timed after the start, as an appointment moved to before an ordinary booking is. Any recorded reopening counts, one made after the start included, as it does for admission: an appointment cancelled after its start and put back gets no further text or email, whether or not the worker saw the cancellation (a seen cancellation ends the run, and a run is carried on only for a time still to come). Counting only a reopening made while the appointment was ahead would make that answer depend on when the worker ran. A Create task step after the start still does: when the worker did not see the cancellation its task is created, and when it did the run has ended and none is.
- **A reopening lost to a capture gap** (known limitation, kept this round). When the save that reopens a cancelled appointment is not recorded (its capture timed out or failed and left a gap row), both its retraction and its change-log entry are missing. The slot still reads as cancelled, so nothing resumes then. The next recorded save that opens the appointment after a recorded change of status, such as a No Show recorded and then taken back, counts as the reopening. The run the cancellation stopped carries on from it, a booking first processed while cancelled is admitted at it, both are paced from it, and the one 'reopened' event comes from that save. Reminders resume later than with a complete record; in the cases tested nothing went out twice.
- **A booking first processed while No Show or Completed** (known limitation, kept this round). When a person marks the appointment No Show or Completed before the worker processes its booking, or enters it with that status, admission refuses the booking. Taking the outcome back is not a reopening, because there was no cancellation, so the appointment gets no reminders. The same saves seen by the worker in time keep their run.
- **An outcome with no record taken back after the seven-day hold** (known limitation, found this round, as before it). The calendar's own No Show or Completed holds a booking's message when the slot record has no outcome for it: after a save with no signed-in person, a capture gap, or a person's move while the outcome stood. Held like that for more than seven days before the start, the hold ends the run. A later save that sets Scheduled then records no take-back and no reopening, so the worker is not told, the run is not carried on, and the time gets none of its remaining reminders (scenarios Z9 620, Z13 630, Z6 660 and X8 671). A change to Cancelled and a reopening does tell it. Having the change-log observer (`private.automation_capture_appointment_reopened`) also report a save that leaves the appointment open after No Show or Completed fixes this (tested); the observer is pinned, so that needs regenerated rollbacks.
- **An ordinary move processed after its run finished** (known limitation, kept this round). A run of an automation with no appointment wait (a plain wait, then a task or a message) records no slot. When the appointment is moved and that run finishes before the worker processes the move, the new slot's booking starts a second run, which repeats the run's steps; seen in time, the run follows the move and nothing repeats. This follows from the decision above that an ordinary move counts from its own booking and that a run that finished for an earlier time does not block the new time. Only a reopening checks for a run that already followed the slot; adding that check to an ordinary booking would change that decision.
- **A No Show or Completed taken back by a save that also moves the appointment** (known limitation, as before this round). When the appointment was not cancelled since it last stood, such a save is not a reopening, so the new slot's booking is an ordinary one: it counts its stop rules from that save and does not check for a run that already followed that time. When the appointment is marked No Show, moved while No Show and then moved back by one save that writes Scheduled (the sync's, for example), the follow-up a run already gave for that time starts again, also after a reply while it was No Show for an automation that stops on a reply. This follows from two rules above: a No Show taken back without a cancellation is not a reopening, and an ordinary booking counts from itself. It lies on admission's ordinary path, which this round does not change (scenario z4, leads 385 and 386, and the remaining random-walk findings).
- **A person's stop during the sync's rewrite** (known limitation, found this round). The change log dates when the appointment first stood at a slot. When one save moves the appointment and cancels it, the sync then writes Scheduled over that, and an Admin stops the run, all before the worker processes any of it, the change log reads open from the sync's save although the slot still holds the person's cancellation. The stop then holds for the new slot, and admission reads the change log's time at the stop the same way, so once the cancellation is taken back the new time gets no reminders (scenario z2, lead 396), for an automation with no appointment wait too. Without the sync's save the new time starts over. Changing this belongs with the owner's decision on the sync's saves.
- **An Admin's stop sent while a reopening carries the run on** (known limitation, as before this round). When an Admin stops a run while the worker's refresh is carrying it on, the stop reads the run as already stopped and fails ("Running automation unavailable"); after the refresh commits, the run goes on. Nothing is sent twice, but the stop must be sent again. The same applies while the carry-on takes up a run after an outcome is taken back (scenario race4 HC). Taking the contact's automation lock in the stop, as the refresh and admission do, would make it wait instead; the stop is pinned, so that change needs regenerated rollbacks.
- **A person's stop made before the worker processed an ordinary move** (known limitation, found this round). A person's stop made after an ordinary move was saved but before the worker processed it does not hold the new time: the worker starts the automation over for it, so a reminder already given there goes out again (scenario V7G 640), or, when the stop and the worker's move back overlap, the stop succeeds and the replaced run still carries on (race3 RE). It lies on admission's ordinary path, which this round does not change; a fix there would let a run a person stopped after the new booking's own save hold that booking's time.
- **The slot record's outcome lookup has no index** (follow-up, found last round). `private.appointment_outcome_events` has no index on `occurrence_id`, so finding a slot's latest outcome scans the table when the slot has none: at 100,000 outcome rows an appointment-state call takes about 6 ms on an idle machine (33 to 36 ms under load), against under 1 ms with an index. The state is read on every claim, stop check and refresh of an appointment run. The index belongs with the evidence package, or in a V2 migration whose rollback drops it. A retype chain is walked one record at a time, so a state call grows with the chain: about 2 to 3 ms with 100 retypes on current statistics; real chains are one or two retypes.
- **A time a finished run passed through and then left** (known limitation, decided this round). A run that completed or failed holds only the time it ended at (a failed run, only once it gave something other than the message that failed), and a run the automation started over from (recorded as rescheduled) holds none, so a reopening back at a time it gave reminders for before it followed another time starts over there too (walk y10a seed 0.579, lead 507, the same before this round). When it gave part of one time's sequence and then followed another time (carried on there by a reopening, or kept its place through an ordinary move), a reopening back at the first time starts the sequence over, so what it gave there is given again (scenarios w1 503, 505 and 506 and W1 521; suite lead 269). So does the take-back after the seven-day hold when it carries on there a later run that had not reached an appointment wait and followed an ordinary move back to that time, as that run would without the outcome, and likewise when a stop rule ended the earlier run that gave there, since such a run holds no time (scenarios M2 935, M4 949, W1 961 and 962; a stricter take-back that also passes over a time another booking run of the automation gave something at was tested and passes the appointment suite, and is left for the owner). Holding that time instead would leave the current time without reminders it is still owed. The follow-up design is a record of what was given for which time, step by step, so that a restart there skips exactly those steps.
- **A first reminder sent late twice after an ordinary move back** (the ordinary-move decision). After an ordinary move started the automation over for another time and its run handed off the first reminder, an ordinary move back to the first time starts over again, so a first reminder sent late goes out twice for that time (scenario W1, lead 533; suite lead 262). A move back made while the appointment was cancelled and its reopening do not (W1 531 and 532).
- **A run with no appointment wait that follows an ordinary move back** (known limitation, found this round, as before it). A run that has not reached an appointment wait follows every ordinary move in place, and nothing asks whether another booking run of the automation holds the time it follows. So after an ordinary move started the automation over, an ordinary move back to a time where an earlier run already gave the sequence gives it there again (scenario Q1 950), also when a person stopped that earlier run there (scenario W7 972), and a cancellation and reopening on that slot afterwards carries the run on there all the same (Q1 952). After the seven-day hold ended such a run and the outcome was taken back, the take-back's guard keeps the time to one sequence when that earlier run holds it (lead 308; scenario W7 971). Checking the held-time rule (`private.automation_time_held`) when such a run follows a move back would fix it in the unpinned refresh; it changes the ordinary-move decision, so it is left for the owner.
- **A finished follow-up with no appointment wait holds its booking's time** (decision, as last round). Such a run records no slot, so its booking's time counts as one it ended at, even when the appointment was moved before the run gave anything. Booked at T1, moved to T2 where the follow-up is given, then moved back to T1 while cancelled and reopened, T1 gets no second follow-up (scenario N1, lead 411).
- **Runs are compared per automation, across republished versions** (known limitation). The held-time rule compares runs, not steps, across every version of the automation, so a version republished with an extra reminder gets nothing at a time a run of the previous version finished at (scenario N4, lead 472).
- **The change log read for saves in an ignored status** (performance, as before this round). When the appointment first stood at its slot, and the change log's standing save (`private.automation_stood_at`), each look back for a cancellation since the save that last left the appointment open, for every save in a status the outcome record ignores, so a long run of such saves costs quadratically: about 2.5 s for one read after 1,000 consecutive such saves following a cancellation (2.4 s before this round). The other measured patterns stay under 1 ms, except 30,000 consecutive cancellations (about 150 ms, as before). One ordered pass over the change log would bound it.
- **The guard's cancellation exclusion is NULL-safe but untested** (known). The first-processed guard passes over a stopped run whose reason is 'Appointment was cancelled', written NULL-safely; no writer stores a stopped run without a reason, so no test can tell that form from the plain one. A check that a stopped run has a reason, in a later migration whose rollback drops it, would make the case impossible.
- **A cancellation the worker never saw** (known limitation, as before this round). It stopped no run, so nothing is carried on when the appointment stands again: a plain wait that ended while the appointment was cancelled keeps that end, and the task after it is due then. A worker that saw the cancellation would pace it from the reopening. Floors for live runs on every reopening would change runs that never stopped.
- **Two more known limitations** (not fixed this round, as before it). A booking a paused automation kept for its resume (no run of it followed the appointment), then moved by an ordinary move during the pause, is not followed after the resume, so the appointment gets no reminders (scenario N3, lead 520); a run that was carried on follows the move (lead 521), and an automation that was not paused follows it. An appointment moved away and back, with a conversation or reply in between, all before the worker saw the move away, starts the reminders over for the unchanged time and gives the first one again.
- **An outcome correction or a move the slot record missed** (known limitation, found this round, as in every earlier version). When a no-show or held outcome started a follow-up and a later save changed the outcome (for example to Completed or Cancelled) or moved the appointment while the outcome capture was off or timed out, the slot record still shows the first outcome on an open slot and the follow-up is still sent: after a missed move until the appointment's next save closes the stale slot and the run ends as rescheduled, after a missed outcome change unless a later save changes the status again. A deletion the record missed does end such a run ("Appointment was removed"). Treating a calendar status that differs from the run's outcome as a change needs a decision on status saves made by background processes.
